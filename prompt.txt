## BLOCKER 1 — Rejected activity matches must not create activity provenance

Current `EvidenceRepository.listByActivityId()` derives evidence from `activity_matches` without filtering by match status.

The current query effectively does:

```sql
WHERE e.project_id = ?
AND (
  e.id IN (
    SELECT am.evidence_id
    FROM activity_matches am
    WHERE am.project_id = ? AND am.activity_id = ?
  )
  OR e.progress_update_id IN (
    SELECT am.progress_update_id
    FROM activity_matches am
    WHERE am.project_id = ? AND am.activity_id = ?
  )
  ...
)
```

This is incorrect.

Pass 9 established:

```text
suggested = not accepted
confirmed = accepted
rejected = explicitly rejected
```

A rejected match must NEVER make evidence appear as originating evidence for the activity.

### Required behavior

For provenance obtained through `activity_matches`:

```text
confirmed → may contribute activity provenance
rejected  → MUST NOT contribute activity provenance
suggested → MUST NOT be treated as accepted provenance
```

Do not reinterpret rejected matches.

The existing historical-progress path remains valid:

```text
ActivityProgress
    ↓
progressUpdateId
    ↓
Evidence
```

because canonical ActivityProgress is already subject to Pass 10 match-status rules.

### Required implementation

Modify `listByActivityId()` so match-based evidence provenance is restricted to accepted/confirmed matches.

Be careful that BOTH of these paths respect match status:

```text
ActivityMatch.evidenceId
ActivityMatch.progressUpdateId → Evidence.progressUpdateId
```

Do not merely filter the direct `evidence_id` subquery while leaving the `progress_update_id` subquery unrestricted.

### Required regression tests

Add a test with:

```text
Progress Update U1
Evidence E1 attached to U1
Activity A1
ActivityMatch M1:
    progressUpdateId = U1
    activityId = A1
    status = rejected
```

Then:

```text
GET /api/projects/<projectId>/activities/<activityId>/evidence
```

must NOT return E1 solely because of the rejected match.

Also test:

```text
suggested → no accepted match provenance
confirmed → provenance is returned
```

Preserve the existing successful traceability test.

# BLOCKER 2 — Evidence deletion can leave DB/file inconsistency

Current `DefaultEvidenceService.deleteEvidence()` removes the physical file FIRST and only then deletes the SQLite evidence row.

Current sequence:

```text
get evidence
↓
unlink physical file
↓
delete DB row
```

This creates an unsafe failure mode:

```text
unlink succeeds
↓
SQLite DELETE fails
↓
DB row still exists
↓
physical evidence file is gone
```

The evidence record is now inconsistent and content retrieval fails.

This is not acceptable.

## Required correction

Redesign deletion so a database failure cannot silently leave an evidence row pointing to a missing file.

Remember:

```text
SQLite transaction and filesystem cannot participate in one atomic transaction.
```

Therefore explicitly choose a failure-safe ordering and document it.

A simple acceptable approach is:

```text
1. validate/project-scope evidence
2. perform DB deletion successfully
3. remove physical file
```

but if using this ordering, handle filesystem deletion failures explicitly and define the resulting state. Do NOT silently swallow the failure.

Alternatively, implement a safe temporary-file/rollback strategy.

The important invariant is:

```text
No silent DB/file inconsistency.
```

Do not pretend filesystem deletion is transactional.

## Required deletion tests

Add at least one failure regression test that simulates:

```text
physical file exists
DB deletion fails
```

and verifies the system does not silently report successful deletion while leaving an inconsistent state.

Also preserve the existing successful delete test.

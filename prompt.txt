# PASS 9 Corrective Fix — Preserve Reviewed Activity Matches

Pass 9 is **not yet approved** because the current re-matching idempotency implementation deletes **all** `activity_matches` for a progress update before inserting new suggestions.

That is unsafe because future human-review states already exist in the domain:

```text
suggested
confirmed
rejected
```

A re-run of the automatic matcher must **never destroy a `confirmed` or `rejected` match**.

## Required correction

Inspect the current `ActivityMatchingService` and `ActivityMatchRepository` implementation on `main` before changing anything.

The current behavior is effectively:

```text
rerun matching
    ↓
deleteByProgressUpdateId(projectId, progressUpdateId)
    ↓
insert new suggestions
```

and that deletion currently affects every match regardless of status.

Change this behavior so that automatic re-matching only replaces **automatically generated `suggested` matches**.

The intended lifecycle is:

```text
First matching
    ↓
suggested match

Rerun matching
    ↓
old suggested matches replaced
    ↓
confirmed matches preserved
    ↓
rejected matches preserved
```

Do **not** delete or overwrite human-reviewed state.

---

## 1. Repository change

Modify the activity-match repository so the service can remove only suggestions belonging to a particular progress update/project.

Prefer a narrow method such as:

```ts
deleteSuggestedByProgressUpdateId(
  progressUpdateId: string,
  projectId: string
): number
```

implemented with:

```sql
DELETE FROM activity_matches
WHERE progress_update_id = ?
  AND project_id = ?
  AND status = 'suggested'
```

Keep strict project scoping.

Do not weaken the existing composite foreign-key protections.

Do not remove the existing general deletion methods unless they are demonstrably unnecessary.

---

## 2. Service change

In:

```text
backend/src/services/matching/activity-matching.service.ts
```

change the re-matching logic so it uses the new **suggested-only** deletion behavior.

The persistence flow should become:

```text
calculate new candidates
        ↓
delete previous suggested matches only
        ↓
insert current suggested matches
```

Never do:

```text
DELETE all activity_matches for update
```

The service must continue to persist generated matches as:

```ts
status: 'suggested'
```

and never automatically create:

```text
confirmed
rejected
```

---

## 3. Critical regression tests

Add explicit tests proving reviewed matches survive automatic re-matching.

### Test A — confirmed survives

Set up:

```text
suggested match
```

then change that persisted row to:

```text
status = 'confirmed'
```

run Pass 9 matching again, and verify:

```text
confirmed match still exists
```

Then verify the newly-generated suggestions are also present as expected.

The test must prove the confirmed row was **not deleted and recreated**.

Ideally verify its:

```text
id
status
reviewedBy
reviewedAt
```

remain intact.

---

### Test B — rejected survives

Repeat the same test with:

```text
status = 'rejected'
```

After re-running matching:

```text
rejected match still exists
```

and its review metadata remains intact.

---

### Test C — suggested is replaceable

Keep the existing idempotency behavior for suggestions:

```text
run matching
→ one suggested match

run matching again
→ old suggestion replaced
→ no duplicate suggested rows
```

This test should still pass.

---

### Test D — mixed state

Create:

```text
confirmed match
rejected match
suggested match
```

for the same progress update.

Run matching again.

Expected:

```text
confirmed → preserved
rejected   → preserved
suggested  → replaced
```

This is the strongest regression test and should be included.

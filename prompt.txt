# FieldLine — PASS 21: ACTIVITY DETAIL VIEW

Implement **Pass 21 — Activity Detail View** in the existing FieldLine repository.

Work from the actual current `main`.

Passes 13–20 are approved.

Do NOT implement Pass 22+.

---

# 1. Objective

Give every schedule activity a complete, trustworthy history.

For an activity such as:

```text
Foundation — Block B
```

the user must be able to see:

```text
Current state
────────────────────────
Planned: 75%
Actual: 60%
Variance: -15 pts
Status: AT_RISK

Timeline
────────────────────────
Aug 20 — planned start
Aug 22 — started
Aug 23 — 35%
Aug 24 — 60%

Evidence
────────────────────────
Report-001.pdf
Report-004.txt
```

The page must make the product feel like a real project-management system rather than a collection of AI demos.

---

# 2. Architectural principle

Pass 21 is a **read-only activity detail composition layer**.

It must NOT create new project truth.

Architecture:

```text id="arch21"
Activity Detail Request
        ↓
ActivityDetailService
        ↓
canonical Activity
+
canonical Snapshot/Risk
+
ActivityProgress history
+
ProgressUpdate context
+
Match/review context
+
Evidence provenance
        ↓
typed ActivityDetail response
        ↓
React Activity Detail View
```

Do NOT duplicate domain logic.

Do NOT create a second risk engine.

Do NOT create a second progress engine.

---

Reuse the existing services/repositories.

Important current sources:

# 4. New API

Add:

```http
GET /api/projects/:projectId/activities/:activityId
```

Use a thin Express route.

Validate:

```text id="params21"
projectId
activityId
```

using existing validation conventions.

Cross-project activity IDs must return the existing not-found/project-isolation behavior.

# 5. Activity Detail response

```text

```

with a typed DTO.

```ts id="dto21"
  progressUpdates: ActivityDetailProgressUpdate[];
```

Adapt naming to current repository conventions.

Do not copy the entire database schema into the DTO.

# 8. Optional `asOfDate`

Support:

```http
GET /api/projects/:projectId/activities/:activityId?asOfDate=YYYY-MM-DD
```

Use the same canonical date validation already used by Pass 17 and Pass 20.

If omitted:

```text current canonical date = existing snapshot service behavior
```

If supplied:

```text all current-state fields are evaluated as of that date
```

Do not use wall-clock timestamps for historical project semantics.

# 10. Timeline

The timeline must come primarily from canonical `ActivityProgress` history.

Use:

```text id="history21"
ActivityProgressRepository.listByActivityId(activityId, projectId)
```

or the existing ProgressService wrapper.

Sort deterministically:

```text id="timeline-sort21"
asOfDate ASC
createdAt ASC
id ASC
```

or another canonical chronological ordering consistent with existing repository semantics.

Do not rely on SQLite implicit order.

---

# 11. Timeline item

```text id="timelineitem21"

```

Where source is available, resolve it from the originating ProgressUpdate:

```text

xlsx

```

Do not infer source from filenames.

---

# 12. Timeline semantics

A timeline item represents a canonical ActivityProgress observation.

Example:

```text id="timelineexample21"
Aug 22
started
0%

Aug 23
in progress
35%

Aug 24
in progress
60%
```

Do NOT create timeline events for every `project_event`.

Do NOT turn evidence upload events into progress observations.

Project events can be included as auxiliary audit context later, but they are not the canonical activity progress timeline.

---

# 13. Historical boundary

When:

```text id="boundary21"
asOfDate = D
```

the timeline should not include canonical ActivityProgress observations after D.

Use:

```text observation.asOfDate <= D
```

as the semantic boundary.

Do not use:

```text createdAt <= D
```

as a substitute.

Creation time and effective progress date are different concepts.

---

# 14. Progress update context

For each ActivityProgress item with:

```text progressUpdateId
```

```text id="updatecontext21"

reporterRole

status
```

Do not return the entire project's progress update list.

Only return update records relevant to this activity's history.

# 16. Canonical progress eligibility

For every match/context item, make it obvious whether it represents canonical truth.

Current invariant:

```text id="canonical21"
confirmed match
→ eligible for existing ProgressService

suggested
→ not canonical

unresolved
→ not canonical

rejected
→ not canonical
```

Do not introduce another boolean truth system if the existing status/review state already determines this.

A derived UI field such as:

```text
canonicalProgressEligible: boolean
```

is acceptable only if it is deterministically derived from current status semantics.

# 17. Evidence

At minimum:


---

# 18. Evidence relationship

Do not simply query:

```text id="bad21"
all project evidence
```

Instead use:

```text id="good21"
EvidenceRepository.listByActivityId(activityId, projectId)
```

or an equivalent project-scoped provenance query.

The returned Evidence list must represent actual activity provenance.

---

# 19. Do not duplicate evidence

An evidence item referenced by several updates should not appear as uncontrolled duplicates in the final DTO.

Deduplicate by:

```text id="dedupe21"
evidenceId
```

while preserving deterministic ordering.

Prefer newest upload first for the evidence section unless existing repository semantics dictate otherwise.

---

# 20. Repository efficiency

Do not introduce an N+1 query pattern inside ActivityDetailService.

The target activity detail is one activity, so a small number of bounded queries is acceptable.

Use:

```text id="queries21"
1 activity lookup
1 current snapshot/risk composition
1 activity progress-history query
1 relevant match query
1 relevant evidence query
bounded ProgressUpdate lookup
```

If there are multiple progressUpdateIds, prefer a batch lookup for their ProgressUpdates rather than one query per history item.

Do NOT issue:

```text id="n1-21"
N progress-update queries
```

inside the timeline loop.

---

# 21. Preferred batch method

If `ProgressUpdateRepository` does not already support it, add:

```ts id="batch21"
listByIds(ids: string[], projectId: string): ProgressUpdate[]
```

or an equivalent project-scoped batch query.

Requirements:

```text
project_id = ?
id IN (...)
```

with deterministic ordering.

Empty IDs:

```text
[]
```

must return cleanly without unnecessary SQL.

Do not introduce a generic data-access framework.

# 31. `asOfDate` semantics

If the detail view allows an as-of selector, pass that date to the backend.

If omitted, use canonical current date behavior.

For historical views:

```text id="historical21"

```

Do not incorrectly rewrite evidence upload dates or hide provenance simply because the user is inspecting historical activity state.

If this distinction creates ambiguity, label it clearly rather than inventing historical evidence availability.

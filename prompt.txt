# Pass 8 objective

Convert messy field-report language into **structured field facts**.

Example input:

```text
Foundation work at Block B is 60% complete.
Concrete pouring started today.
```

Conceptual output:

```json
{
  "items": [
    {
      "reference": "foundation work",
      "location": "Block B",
      "progress_percent": 60,
      "status": "in_progress"
    }
  ]
}
```

The important architectural distinction is:

> AI extracts facts from the report. It does NOT decide which scheduled activity the report belongs to.

Activity identity belongs to **Pass 9 — Activity Matching Engine**.

# 2. Define a FieldLine-specific extraction contract

The current generic AI extraction contract is not the Pass 8 domain contract.

Create a dedicated contract for field-progress extraction.

Recommended location:

```text
backend/src/ai/contracts/field-progress-extraction.contract.ts
```

Use Zod.

The contract should represent:

```ts
{
  items: [
    {
      reference: string,
      location: string | null,
      progress_percent: number | null,
      status: ...
    }
  ]
}
```

Use a strict status enum.

Recommended values:

```text
unknown
not_started
in_progress
completed
delayed
```

Use:

```text
progress_percent: number | null
```

with:

```text
0 <= progress_percent <= 100
```

### Bounded output

Do not allow unbounded AI output.

Use a bounded maximum number of extracted items.

Recommended:

```text
maximum 20 items
```

Also enforce reasonable maximum lengths for:

```text
reference
location
```

Recommended limits:

```text
reference <= 200 characters
location <= 200 characters
```

Do not accept arbitrary nested structures.

Do not use `.passthrough()` for the extraction contract.

The final parsed object should contain only the expected fields.

# 3. Be conservative about missing information

The AI must NOT invent facts.

Rules:

### `reference`

Extract the human-readable work reference mentioned in the report.

Example:

```text
"foundation work"
"concrete pouring"
"Pier P12 excavation"
```

Do NOT turn it into an activity ID.

Do NOT generate identifiers such as:

```text
ACT-001
WBS-3.2.4
activity_123
```

unless the report explicitly contains such a value as ordinary text.

### `location`

Extract only if explicitly present.

Otherwise:

```json
null
```

### `progress_percent`

Extract only when explicitly stated or unambiguously represented in the field report.

Do NOT calculate progress from language such as:

```text
"work has started"
"nearly finished"
"making good progress"
```

Those phrases may support a status, but they do not justify inventing a numeric percentage.

If no defensible percentage exists:

```json
null
```

### `status`

Infer only from the report language.

Do not fabricate a status when the report is genuinely ambiguous.

Use:

```text
unknown
```

where appropriate.

# 4. Prompt design

Create a dedicated extraction prompt builder.

Recommended location:

```text
backend/src/ai/services/field-progress-extraction.service.ts
```

or an equivalent clearly separated FieldLine AI service module.

Keep the prompt explicit and deterministic.

The prompt should instruct the model:

```text
You are extracting structured facts from a construction/infrastructure field progress report.

Extract only information explicitly supported by the report.

Do not invent activity IDs.
Do not perform schedule matching.
Do not select an existing project activity.
Do not calculate project truth.
Do not calculate progress from unsupported language.
Do not infer quantities that are not present.

Return only the requested JSON structure.
```

The prompt must make the distinction explicit:

```text
reference ≠ activity identity
```

For example:

> "foundation work" is a textual work reference, not an activity ID.

The model must return the structured contract only.

Do not ask the model for explanations outside the JSON contract.

# 5. FieldProgressExtractionService

Create a dedicated application-facing service responsible for the FieldLine extraction operation.

Recommended:

```text
backend/src/ai/services/field-progress-extraction.service.ts
```

Conceptually:

```ts
extractFromReport(rawText: string): Promise<FieldProgressExtraction>
```

Responsibilities:

1. Validate the input is a non-empty string.
2. Enforce a reasonable maximum raw input length.
3. Build the explicit extraction prompt.
4. Call the existing `AIService.extractStructured(...)`.
5. Return the validated structured extraction result.
6. Translate provider/extraction failures into the existing application error model where appropriate.

It must NOT:

* query SQLite
* import repositories
* access activities
* access schedules
* mutate `progress_updates`
* mutate `activities`
* mutate `activity_progress`
* create `activity_matches`
* calculate variance
* calculate risk
* call Pass 9 logic

# 8. API exposure

The extraction capability must be callable so that the workflow can be tested and demonstrated, but keep the endpoint narrowly scoped.

Add a dedicated endpoint only if the existing application architecture has no better existing entry point.

Recommended:

```text
POST /api/ai/field-progress/extract
```

Request:

```json
{
  "rawText": "Foundation work at Block B is 60% complete."
}
```

Response:

```json
{
  "extraction": {
    "items": [
      {
        "reference": "foundation work",
        "location": "Block B",
        "progress_percent": 60,
        "status": "in_progress"
      }
    ]
  }
}
```

### API rules

Validate the request with Zod.

Reject:

* missing `rawText`
* empty `rawText`
* whitespace-only `rawText`
* excessively large `rawText`

Return an appropriate application error when AI extraction fails.

Do not persist the extraction.

Do not require a project ID for this endpoint unless the existing architecture demonstrates a concrete reason to do so.

Do not attach the extraction to a scheduled activity.

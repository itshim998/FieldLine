Your task is to migrate FieldLine from a Render-filesystem-backed SQLite production database to a **persistent Supabase PostgreSQL production database**, while preserving the existing application architecture and all currently implemented behavior.

## Current authoritative baseline

The latest GitHub `main` commit is:

```text id="x8g1v2"

```

Commit:

This commit already contains the completed Phase 1–4 architecture, including:

* Resend HTTP email delivery
* notification outbox
* notification worker

# 2. IMPORTANT: THIS IS NOT A SIMPLE DATABASE-CONFIG CHANGE

The current database layer uses synchronous `better-sqlite3`, SQLite-specific transactions, PRAGMA settings, SQLite error codes, and a custom SQLite migration system.

Therefore, do not assume that replacing:

```text id="7y0c1j"

```

with:

```text

```

is sufficient.

The PostgreSQL implementation will require asynchronous database access.

Perform a full architecture audit first and determine the smallest safe migration strategy.

# 6. CHOOSE THE CORRECT SUPABASE CONNECTION MODE

Do not hard-code assumptions.

Supabase currently supports:

* direct Postgres connection
* shared pooler session mode
* shared pooler transaction mode
* dedicated pooler modes on applicable plans

For a persistent Render backend, determine whether direct connectivity is appropriate.

If the deployment environment is IPv4-only, use Supabase's shared pooler in **session mode** rather than assuming IPv6 direct connectivity.

Use a connection configuration that preserves the transaction semantics required by FieldLine.

SSL must be enabled for remote production connections.

The same `DATABASE_URL` abstraction should support the chosen connection mode cleanly.

# 8. ASYNC MIGRATION

This is a major part of the work.

The current SQLite repositories are synchronous.

PostgreSQL access will be asynchronous.

Convert repository contracts to async where necessary:

```ts id="c4gh3b"
await repository.getById(...)
await repository.create(...)
await repository.list(...)
await repository.update(...)
```

Then propagate `async/await` through the affected service/controller paths.

Do NOT create:

```text
sync wrappers around async DB operations
```

using hacks such as child processes, blocking loops, or arbitrary synchronous network workarounds.

Do not hide asynchronous database calls behind unsafe pseudo-synchronous abstractions.

Use normal Node asynchronous I/O.

# 13. TRANSACTION MIGRATION

Replace SQLite-specific transaction logic with native PostgreSQL transactions.

The important invariant is:

```text id="lvn2wc"
BEGIN
    persist anomaly/activity match
    create notification_outbox row
COMMIT
```

The external providers MUST NOT be called inside the database transaction.

Never do:

```text id="6k0lfx"
BEGIN
    DB writes
    ↓
    Resend HTTP request
    ↓
COMMIT
```

Instead:

```text id="p2wtgd"
BEGIN
    DB writes
    outbox insert
COMMIT

Notification worker
    ↓
external provider
```

The notification outbox must remain atomically coupled to anomaly persistence.

---

# 14. POSTGRES TRANSACTION CLIENT/PINNING

When using a PostgreSQL pool, transaction operations must execute on the same checked-out connection/client.

Do not accidentally run:

```text id="tw5r1s"
BEGIN on connection A
INSERT on connection B
COMMIT on connection C
```

The transaction helper must guarantee a single connection for the entire transaction.

Test this.

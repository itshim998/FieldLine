# 1. BLOCKER — CONFIRMED MATCH HISTORY MUST NOT BE MUTATED

The current repository method:

```text
ActivityMatchRepository.updateMatchReview(...)
```

can modify:

```text
activity_id
status
match_method
rationale
review_state
reviewed_by
reviewed_at
```

in place.

This creates a serious provenance problem.

Example:

```text
Match M1
activityId = Foundation B
status = confirmed
        ↓
ProgressService
        ↓
ActivityProgress references M1 / Foundation B
        ↓
later /resolve M1
        ↓
activityId = Foundation C
```

Now the historical match says Foundation C while the canonical progress was created for Foundation B.

That must never happen.

The same problem exists if an already-confirmed match can later be rejected.

## Required invariant

Once a match is confirmed or rejected, its historical decision must not be silently rewritten.

Required state rules:

```text
suggested + awaiting_review
    → confirm
    → reject

suggested + unresolved
    → resolve
    → reject

confirmed
    → immutable historical decision

rejected
    → immutable historical decision
```

A confirmed match MUST NOT be retargeted with `/resolve`.

A confirmed match MUST NOT be retroactively rejected.

A rejected match MUST NOT be silently confirmed.

---

# 2. Review operations must enforce legal state transitions

Do not rely only on frontend behavior.

The backend service must enforce the transition matrix.

Define a central transition policy, for example:

```text
suggested + awaiting_review
    → confirmed
    → rejected

suggested + unresolved
    → confirmed via explicit resolve only
    → rejected

confirmed
    → no further mutation

rejected
    → no further mutation
```

The exact names may differ based on the current model, but the semantics must be equivalent.

Invalid transitions must raise a deterministic `ValidationError`.

Examples:

```text
confirm(confirmed)
→ reject

reject(confirmed)
→ reject

resolve(confirmed, differentActivity)
→ reject

confirm(rejected)
→ reject

resolve(rejected)
→ reject
```

Do not create silent no-ops.

# 3. Do NOT rewrite historical ActivityMatch records

When a low-confidence match is manually resolved:

Current candidate:

```text
activityId = weak/initial candidate
confidenceScore = 0.41
matchMethod = text_similarity
```

Human chooses:

```text
activityId = ACT-203
```

It is acceptable to transition that unresolved record to a human-resolved confirmed state **only if it has not yet become canonical progress and the record is clearly still a review candidate**.

But once a match has become a confirmed historical decision that may already be referenced by ActivityProgress, it must not be retargeted.

Before implementing this, inspect how `ActivityProgress` references matches in the current schema and repository.

Prefer the smallest change that guarantees historical consistency.

If the current model cannot guarantee this cleanly, introduce an immutable review-resolution record or create a new manual match record rather than rewriting an existing confirmed record.

Do not introduce unnecessary architectural complexity.

---

# 4. Review actions and audit events MUST be atomic

Current review operations do this conceptually:

```text
UPDATE activity_matches
        ↓
try create project event
        ↓
catch error
        ↓
log and continue
```

This is unacceptable for an auditable review system.

A successful review action must never exist without its corresponding audit event.

The same applies to automatic confirmation and match suggestion events where those events represent the state transition being recorded.

---

# 5. Required transaction boundary

For each state-changing review operation:

```text
BEGIN TRANSACTION

1. verify target row/project/state
2. update activity_matches
3. insert corresponding project_event

COMMIT
```

If step 2 or step 3 fails:

```text
ROLLBACK
```

The API must return an error and the match must remain in its previous state.

Do NOT swallow project-event persistence errors.

Do NOT merely log them.

Do NOT return success after an audit write failure.

At minimum:


must have atomic state + audit persistence.

For example:

```text

```

```text

ALL IN ONE TRANSACTION
```

Manual resolution:

```text

matchMethod → manual
status → confirmed
reviewState → resolved
reviewer metadata
projectEvent → match_resolved

ALL IN ONE TRANSACTION
```

# 8. Repository/service design

Prefer a repository method that performs the state transition and audit insertion in the same SQLite transaction rather than making the service perform two independent writes.

For example:

```ts

```

or:

```ts

```

Choose the smallest clean abstraction consistent with the existing repository architecture.

Do not introduce a generic transaction framework.

Reuse the existing SQLite transaction utilities if the repository already has them.

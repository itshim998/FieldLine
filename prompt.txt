# 1. Objective

Expand FieldLine's progress-capture workflow beyond manually entered text.

The new pipeline must become:

```text
Evidence file
      ↓
document validation
      ↓
format-specific extraction
      ↓
normalized text/data
      ↓
ProgressUpdate
      ↓
existing AI field-progress extraction
      ↓
existing activity matching
      ↓
existing deterministic progress normalization
      ↓
ActivityProgress
```

Pass 14 is the **document-to-text/data ingestion bridge**.

Do NOT duplicate or redesign the existing:

* Evidence system
* AI extraction system
* Activity matching engine
* Progress normalization
* Planned-vs-actual engine
* Risk engine

Reuse them.

# 8. Define a normalized ingestion contract

Create a typed internal representation for extracted document content.

Conceptually:

```ts
interface NormalizedDocument {
  evidenceId: string;
  projectId: string;
  sourceFileName: string;
  sourceType: 'csv' | 'xlsx' | 'pdf' | 'image';
  text: string;
  metadata?: Record<string, unknown>;
}
```

You may adjust the exact contract to fit the existing project.

Important:

* `text` must be deterministic and bounded
* preserve useful source context
* do not let format-specific code leak into the AI service
* preserve the originating `evidenceId`

For tabular documents, the normalized text may contain:

```text
Sheet: Daily Progress

Date | Activity | Location | Quantity | Status
2026-08-25 | Pier P1 Concrete | Zone A | 100 m3 | In Progress
...
```

The exact serialization format should be deterministic and readable by the downstream extraction service.

# 9. CSV ingestion

Implement CSV field-report ingestion using the existing `csv-parse` dependency.

Do NOT treat CSV ingestion as schedule import.

Pass 4/5/6 already handle schedule CSVs.

Pass 14 must interpret CSV as an **evidence document**, not as a schedule.

For CSV:

```text
file
 ↓
validation
 ↓
CSV parser
 ↓
rows
 ↓
normalized tabular text
```

Requirements:

* handle UTF-8 text correctly
* support headers when present
* preserve row order
* normalize empty cells consistently
* bound maximum rows/cells/text size
* produce useful validation errors for malformed CSV
* prevent pathological inputs from producing unbounded AI prompts

Do not silently invent missing values.

Do not implement spreadsheet semantics for schedules.

This is field-evidence ingestion.

# 18. Matching and progress execution

Do not automatically force document ingestion all the way through ActivityProgress unless the existing human-review semantics allow it safely.

The existing system deliberately distinguishes:

```text

```

and ProgressService currently permits suggested matches only with explicit `allowSuggested`.

Therefore preserve this trust boundary.

A safe Pass 14 workflow is:

```text
file
↓
normalized text
↓
ProgressUpdate
↓
AI extraction
↓
suggested activity matches
↓
human review
↓
existing ProgressService
```

If you implement automatic progression after matching, it must strictly reuse the existing confirmation/`allowSuggested` policy and must not bypass review semantics.

Prefer the safer design above.

# 20. Failure semantics

Pass 14 must never corrupt project truth.

Examples:

### Unsupported document

```text

↓
processing fails clearly
↓
no fake ProgressUpdate
```

### PDF extraction failure

```text
Evidence remains intact
ProgressUpdate is not created from fabricated text
```

### OCR failure

```text
Evidence remains intact
processing returns an explicit failure
```

### AI extraction failure

Use the existing AI service's failure semantics.

Do not create fake facts.

Do not create ActivityProgress from failed extraction.

### Matching failure

Do not fabricate activity identity.

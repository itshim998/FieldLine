## 7. Filesystem safety

Storage must be project-scoped:

```text

  <project-id>/

```

Never write using:

```text

```

as the actual path.

Never allow:

```text

```

Do not expose arbitrary filesystem paths through the API.

## 11. Atomicity and failure handling

Evidence creation spans:

```text
filesystem
+
SQLite evidence row
+
project event
```

SQLite can transactionally protect the DB records.

The filesystem is not part of the SQLite transaction.

Design the operation so common failures do not leave inconsistent state.

Preferred ordering:

```text
validate everything first
        ↓
write generated file
        ↓
SQLite transaction:
    INSERT evidence
    INSERT evidence_uploaded event
        ↓
success
```

If the SQLite transaction fails after the file was written:

```text
delete the newly written file
rethrow the original application error
```

Do not silently swallow cleanup failures; log them using the existing logger if appropriate, while preserving the original operation error.

Do not create an evidence DB row pointing to a file that does not exist.

Do not leave successful DB rows pointing to failed uploads.

## 12. Idempotency boundary

## 15. Important provenance rule

Do not force a single evidence record when several evidence records legitimately belong to the same progress update.

A progress update may have multiple pieces of evidence.

Return the complete applicable evidence set.

Likewise, an activity may have multiple historical progress observations and multiple originating evidence records.

Do not collapse historical provenance into "latest evidence" unless the existing model explicitly requires it.

PASS 28 — Assistant Response Formatting & Markdown Rendering
Objective

Make every real-AI Assistant response visually polished, readable, structured, and presentation-ready without changing the underlying truth/grounding architecture.

The desired result is:

Question
   ↓
Groq GPT-OSS 20B
   ↓
well-structured Markdown
   ↓
safe Markdown renderer
   ↓
beautiful formatted response

The AI should remain responsible for content structure.

The frontend should remain responsible for visual rendering.

1. Markdown must become the Assistant's response format

For natural-language Assistant answers, establish Markdown as the canonical presentation format.

The model should be encouraged to use:

headings
bold emphasis
italic emphasis where useful
paragraphs
numbered lists
bullet lists
blockquotes where genuinely useful
inline code where relevant
Markdown tables where tabular comparison is useful

Do not force Markdown into every answer.

A simple greeting should remain simple.

A complex project-management answer should become structured.

2. Preserve the structured JSON contract

This is important.

Do not change the outer structured response from:

{
  "answer": "..."
}

for general answers.

Instead, the answer field should contain Markdown:

{
  "answer": "## Recommended approach\n\nStart by identifying the critical path..."
}

For grounded answers, preserve:

{
  "claims": [...]
}

while allowing the existing text/answer content to use Markdown where appropriate.

The JSON itself remains machine-readable.

3. Prompt the real Groq model for polished Markdown

Update:

buildGeneralAnswerPrompt()
buildGroundedAnswerPrompt()

and any other assistant-generation prompts that produce user-visible natural language.

Add a clear presentation contract.

Conceptually:

Return natural-language content as GitHub-Flavored Markdown.

Formatting rules:
- Use a clear heading when the response has multiple sections.
- Use short paragraphs rather than dense blocks.
- Use bullets or numbered lists for multiple items.
- Use Markdown tables when comparing 3+ related attributes or presenting structured tabular information.
- Keep table columns concise.
- Use bold to emphasize important conclusions, not every sentence.
- Put blank lines between paragraphs, headings, lists, and tables.
- Do not return raw HTML.
- Do not wrap the answer in a Markdown code fence.
- Do not emit literal "\n" sequences as visible text.
- Do not use excessive decorative symbols.
- Do not create a table when a normal list is clearer.

This should be applied differently to:

General / advisory answer

Allow natural Markdown.

Grounded project answer

Allow Markdown but preserve factual constraints.

The Markdown is presentation.

The claims remain authoritative structured data.

4. Use GitHub-Flavored Markdown

Use a mature React Markdown renderer rather than writing your own parser.

The desired stack should be something like:

react-markdown
+
remark-gfm

remark-gfm gives you the important table/list behavior required for the UI.

GitHub-style Markdown supports tables using pipes and hyphens, with alignment syntax and escaped pipes where necessary.

Do not enable raw HTML rendering unless there is an explicit requirement.

That means avoid adding:

rehypeRaw

without a strong reason.

The Assistant's Markdown should be treated as untrusted model output.

5. Add a dedicated Markdown renderer component

Do not keep the rendering logic directly inside the huge App.tsx.

Create something like:

frontend/src/components/assistant/AssistantMarkdown.tsx

or follow the repository's existing component naming conventions.

Its responsibility:

Markdown string
    ↓
React Markdown
    ↓
styled semantic elements

Support:

h1
h2
h3
p
strong
em
ul
ol
li
blockquote
code
pre
table
thead
tbody
tr
th
td
a

No raw arbitrary HTML.

6. Markdown CSS should match FieldLine

Create a dedicated class, for example:

.assistant-markdown

Do not globally restyle every paragraph/table in the application.

The Markdown surface should have carefully tuned:

Typography
readable font size
approximately 1.65–1.8 line-height
slight letter spacing
appropriate heading hierarchy
strong contrast without looking oversized
Paragraphs

Use visible separation between paragraphs.

Headings

Give each heading breathing room above and below.

Lists

Proper indentation and spacing between list items.

Tables

Tables should have:

visible borders/dividers
consistent cell padding
aligned headers
compact but readable text
horizontal scrolling on narrow screens
Code

Inline code should look different from prose.

Fenced code blocks should scroll horizontally rather than breaking the page.

Links

Readable and clearly interactive.

7. Tables need special handling

This is specifically important from your request.

The renderer should support AI output such as:

| Activity | Actual | Planned | Variance |
|---|---:|---:|---:|
| Crude Pump Foundation | 65% | 100% | -35% |
| PR-07 Steel Erection | 50% | 72% | -22% |

and render it as a real HTML table, not:

| Activity | Actual | Planned |
|---|---|---|
...

as literal text.

Wrap tables in a responsive container:

overflow-x: auto

so long tables work on 390–430px screens.

Do not force tables to fit by making the font microscopic.

8. Avoid the literal \n problem

The screenshots show escaped-looking sequences such as:

\n1.
\n2.

The implementation must ensure that if the model returns actual newlines, they are rendered as actual Markdown newlines.

If the upstream response somehow contains literal backslash+n sequences:

\\n

add a narrowly scoped normalization step before Markdown rendering.

But do not blindly transform arbitrary \n characters inside code blocks.

Prefer fixing the generation/parsing path first.

9. Markdown should NOT affect grounding

This is fundamental.

A response can now look like:

## Schedule Recovery

The most important action is to **focus on the critical path**.

### Current concerns

- ACT-B02 is delayed.
- ACT-C01 is delayed.

But the underlying verification remains:

factRef
field
value

The Markdown renderer must never become part of the factual validation layer.

Keep:

AI
 ↓
structured claims
 ↓
FieldLine validation

separate from:

answer string
 ↓
Markdown renderer
10. Grounded answers should get especially good structure

For a query like:

What is delayed?

the model should produce something like:

## Delayed Activities

There are **5 delayed activities** as of **30 August 2026**.

| Activity | Actual Progress | Variance |
|---|---:|---:|
| Unit 4 Site Rough Grading | 65% | -35% |
| Crude Pump Foundation Piling Works | 65% | -35% |
| Process Pipe Rack Carbon Steel Spooling | 55% | -20% |
| Cooling Water Header Flush & Hydrostatic Test | 70% | -30% |
| Pipe Rack PR-07 Structural Steel Erection | 50% | -22% |

### Key takeaway

The **Crude Pump Foundation** and **Site Rough Grading** activities require the closest schedule attention.

The exact numbers must still come from verified facts.

The model must not invent the table contents.

11. General answers should also be structured naturally

For:

How to speed up the work?

prefer:

## Ways to Recover Schedule

To accelerate the project, focus first on activities affecting the **critical path**.

### 1. Fast-track

Run compatible predecessor and successor activities in parallel where site conditions allow.

### 2. Add resources

Deploy additional crews or equipment to constrained activities where productivity justifies it.

### 3. Resolve bottlenecks

Prioritize procurement, approvals, access constraints, and contractor dependencies.

### 4. Monitor daily

Use short daily coordination reviews to identify new schedule slippage early.

Not one giant paragraph.

12. Do not over-format

The model should not turn every response into:

# Title

## Section

### Subsection

- Point
- Point
- Point

| table |

A greeting can remain:

Hello! I’m your FieldLine Project Assistant. How can I help?

Use formatting according to complexity.

13. Preserve the AI provider architecture

No changes to:

AIProvider
GroqAIProvider
GroqKeyRouter
MockAIProvider
GeminiAIProvider

The formatting feature belongs above the provider response and/or inside the generation prompt.

The provider should simply return the structured string.

14. Keep MockAI deterministic

Update MockAI's user-visible assistant strings so they can contain the same Markdown structure where appropriate.

But do not make tests depend on real Groq formatting.

For example:

AI_PROVIDER=mock

should still generate deterministic Markdown suitable for renderer tests.

18. Assistant UI hierarchy

The visual hierarchy should become:

AI Assistant Response
        ↓
Natural-language answer
        ↓
Markdown content
        ↓
Verified Facts
        ↓
Fact cards / citations

Keep the current verified-fact cards.

Do not replace them with Markdown.

19. Loading behavior

The user should still see the current Assistant loading state while Groq is processing.

Do not remove the loading skeleton.

The Markdown renderer activates only after the response arrives.

20. Provider/model information

Preserve whatever current safe provider diagnostic exists.

The result should visually communicate something like:

AI Assistant Response
Groq · GPT-OSS 20B

while grounded queries continue showing:

Grounded · 5 Cited Facts

Do not imply that a general advisory response is grounded in deterministic project facts when it isn't.

21. Important security rule

Do NOT render model output using:

dangerouslySetInnerHTML

for Markdown.

Use a proper Markdown AST renderer.

Raw HTML should remain disabled unless there is a specific future requirement.

This also avoids turning Assistant Markdown into an XSS surface.

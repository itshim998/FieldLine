PASS 26 objective

Replace the current real-AI path with Groq openai/gpt-oss-20b, backed by a robust 20-key sequential failover router, while preserving FieldLine's existing AIProvider abstraction, structured-output contracts, canonical-truth rules, deterministic calculations, offline MockAI mode, and regression suite.

The final AI layer should become:

The rest of FieldLine should remain unaware that multiple credentials exist.

4. Stateful sticky key selection

The router needs one central state:

currentKeyIndex

Initial state:

0

meaning Key 01.

For every request:

currentKeyIndex
↓
attempt that key

On success:

keep currentKeyIndex unchanged

On a qualifying failure:

currentKeyIndex = next configured key
retry same request

The same request continues advancing until:

one key succeeds, or
every configured key has been attempted once

Then the request either succeeds or fails.

5. Never restart the ring incorrectly

This is one of the most important robustness requirements.

Suppose:

current = Key 07

and Key 07 fails.

Try:

08 → 09 → 10

If Key 10 succeeds:

current = Key 10

Do not reset to Key 01 after the success.

Likewise, if Key 10 subsequently fails:

11

must be tried next.

The state follows the successful key, not the request count.

6. Failure classification

The router should distinguish between:

Failover-worthy provider failures

Examples:

429 Too Many Requests
authentication/key failures
expired/revoked key responses
transient 5xx responses
network failures
request timeout
provider unavailable
other explicit provider-side failures
Non-failover request failures

For example, a request that is intrinsically invalid because the application sent an invalid payload should not cause the router to permanently rotate through all credentials unnecessarily.

The implementation should classify errors based on actual Groq response/status information.

Groq documents 429 for rate limits and 500/5xx-class provider errors separately from malformed requests.

7. Retry semantics

For a request:

Key 05 → 429

the request should immediately continue to:

Key 06

rather than waiting for Key 05's cooldown.

For transient provider/network failures, continue to the next key according to the failover policy.

When Groq supplies:

retry-after

or rate-limit headers, capture that metadata for diagnostics and router state where useful. Groq explicitly documents headers such as retry-after, x-ratelimit-remaining-*, and x-ratelimit-reset-*.

Do not create an unbounded retry loop.

9. Concurrency safety

This is critical.

Multiple FieldLine requests may arrive concurrently.

The router must not corrupt:

currentKeyIndex

through race conditions.

Design the state transition so concurrent requests have deterministic and safe behavior.

The important invariant is:

A successful request establishes the active key for subsequent requests without another concurrent request accidentally resetting it.

Gemini should specifically inspect the current Node execution model and select an implementation that is safe under concurrent async requests.

10. Key health state

Maintain lightweight runtime state per key:

Key 01
  healthy / failed
  failureCount
  lastFailureAt
  lastSuccessAt
  optional cooldownUntil

Key 02
  ...

This state is in-memory runtime state, not SQLite application state.

Do not create a database table for provider credentials.

11. Temporarily unhealthy keys

A key that repeatedly fails should not necessarily be hammered on every subsequent request.

Implement a lightweight cooldown/health mechanism.

For example:

Key 01 → repeated 429s
        ↓
temporarily unavailable
        ↓
router proceeds through remaining keys

After an appropriate cooldown, Key 01 becomes eligible again.

Do not permanently blacklist a key because of one failure.

The precise cooldown/backoff policy should be based on the provider error type and available reset metadata rather than arbitrary long delays.

12. Expired/revoked credentials

If:

Key 03 → authentication failure

the current request immediately moves to:

Key 04

and Key 03 should be marked unhealthy.

A permanently invalid key should not cause every subsequent request to fail against Key 03 first.

Keep enough state to avoid repeatedly selecting known-dead keys.

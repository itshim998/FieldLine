# 2. HARDEN THE TRUST BOUNDARY BETWEEN PHASE 1 AND PHASE 2

This is the most important correction.

Phase 2 must consume **trusted anomaly facts produced by Phase 1**.

It must NOT independently:

* calculate anomaly scores
* determine severity
* infer whether an activity is anomalous
* reconstruct the canonical baseline
* recompute previous progress from arbitrary database state
* reinterpret Match Model confidence as anomaly evidence
* change severity based on LLM judgment

The intended flow is:

```text
Phase 1 anomaly evaluation
        ↓
trusted structured anomaly result
        ↓
small Phase 2 mapping/adaptation layer
        ↓
GenerateAnomalyMessageInput
        ↓
Groq / deterministic fallback
```

Inspect every caller and verify that they are passing the actual Phase 1 anomaly result rather than manually recreating anomaly facts.

If needed, introduce a small explicit mapper/adapter such as:

`toAnomalyMessageInput(...)`

or an equivalent narrow boundary.

Do NOT duplicate anomaly calculations merely to populate the Phase 2 input.

# 3. SERVER-OWNED FACTS MUST REMAIN SERVER-OWNED

The LLM may generate:

* title
* summary
* details
* recommendedAction
* fullMessage

The LLM must NOT be authoritative for:

* anomalyScore
* anomalySeverity
* activity identity
* activityExternalId
* activityMatchId
* project identity
* observation date
* reporter identity
* previous progress
* current reported progress

These values must come from trusted server-side data.

Prefer this architecture:

```text
trusted server facts
        +
LLM-generated text payload
        ↓
final AnomalyAlertMessage
```

not:

```text
LLM generates everything
        ↓
server trusts the result
```

If the current Zod schema allows the model to generate authoritative metadata, correct it.

# 5. AUDIT THE DETERMINISTIC FALLBACK

The fallback is a critical reliability path.

Verify that fallback messaging:

* never requires Groq
* uses only supplied trusted facts
* never invents missing information
* does not accidentally fabricate `previousPercent`
* does not imply a previous observation when none exists
* does not invent causes
* does not accuse anyone of misconduct
* preserves severity
* preserves the real anomaly score
* produces the same structural contract as the Groq path

Particularly inspect this case:

```text

```

The fallback must NOT produce:

> "Progress increased from X% to 82%"

unless X actually exists.

Instead, it should communicate only what is known.

```text

```

# 6. PRESERVE THE SEMANTIC MEANING OF ANOMALY SCORE

The prompt and output must never imply:

```text
anomalyScore 0.91 = 91% probability of fraud
```

or:

```text
91% chance the worker is wrong
```

or:

```text
91% chance the report is fake
```

The correct interpretation is that the observed progression pattern is statistically distant from the learned/expected progression baseline according to Phase 1.

The model may explain this in natural language, but must not change its meaning.

Add or strengthen tests that catch this class of semantic failure.

# 7. KEEP ACTIVITY MATCH AND ANOMALY AS ORTHOGONAL CONCEPTS

* activity may have been incorrectly identified

This distinction must remain explicit in prompt construction and tests.

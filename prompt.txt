You are now implementing **Phase 3 — Free HTTP Email Delivery** for FieldLine.

The objective is to add a real, free, HTTP-based email delivery channel for the anomaly alerts produced by Phase 2.

The intended architecture is:

```text
Worker Progress Report
        ↓
Phase 1 — Anomaly Detection
        ↓
Persisted anomaly/activity match
        ↓
Phase 2 — AnomalyAlertMessage
        ↓
Phase 3 — Email Delivery
        ↓
HTTPS
        ↓
Resend
        ↓
Administrator Email
```

The architectural rule remains:

**ML detects. Groq explains. Email delivers.**

Do not blur these responsibilities.

# 2. USE RESEND OVER HTTPS

Implement email delivery using the Resend Email API over HTTPS.

Do NOT use:

* SMTP
* Nodemailer
* Gmail SMTP
* a local mail server
* a background email daemon

The current deployment is a Render Free Node web service, so SMTP is specifically unsuitable.

Prefer native Node 22 `fetch()` rather than introducing the Resend SDK unless the existing repository architecture provides a strong reason otherwise.

Keep the dependency footprint small.

Keep Resend-specific behavior behind an adapter such as:


or an equivalent name.

The rest of FieldLine should depend on the abstraction, not directly on Resend.

---

# 10. ANOMALY AND EMAIL FAILURE MUST BE INDEPENDENT

This invariant is mandatory:

```text
Anomaly persistence success
        +
Resend failure
        =
anomaly remains valid
```

For example:

```text
Phase 1 → HIGH anomaly
Phase 2 → message generated
Phase 3 → Resend returns HTTP 503
```

Expected behavior:

* anomaly remains persisted
* dashboard remains correct
* email failure is logged as a delivery failure
* the original worker operation must not be rolled back solely because email failed

Do NOT:

* delete the anomaly
* undo the progress record
* mark the anomaly false
* throw an error that causes the whole worker report transaction to fail

unless the existing application architecture absolutely requires surfacing a non-fatal delivery result. In that case, preserve the anomaly and clearly separate the delivery status.

# 12. USE RESEND IDEMPOTENCY

Resend supports `Idempotency-Key`.

Use a deterministic idempotency key based on the originating anomaly identity, preferably using the actual Phase 2 correlation field such as `activityMatchId` plus an explicit notification purpose.

Do not invent random keys for every retry.

The objective is to reduce duplicate sends for the same anomaly event.

Inspect the actual Phase 2 correlation model before deciding the exact key format.

---

# 13. HANDLE HTTP ERRORS ROBUSTLY

The delivery adapter must handle at least:

* successful 2xx response
* 400 validation errors
* 401/403 authentication/authorization errors
* 429 rate limiting
* 500/502/503 server failures
* network failures
* connection timeout
* invalid/malformed response body

Use an explicit request timeout.

Prefer `AbortController` or another standard Node mechanism.

Do not hang the worker request indefinitely waiting for Resend.

---

# 14. NEVER LEAK SECRETS

The following must never appear in logs or thrown error messages:

* `RESEND_API_KEY`
* `Authorization: Bearer <key>`
* raw secret values

A Resend error should be summarized safely.

For example:

```text

```

is fine.

Dumping the entire request headers object is not.

Add a regression test for secret redaction where appropriate.

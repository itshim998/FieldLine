# 5. Critical semantic distinction

Do NOT classify every activity with negative variance as delayed.

The engine must distinguish:

```text
BEHIND PLAN
```

from:

```text
DELAYED
```

and:

```text
AT RISK
```

Recommended conceptual model:

```text
COMPLETED
    ↓
activity is objectively complete

DELAYED
    ↓
planned finish has passed
AND
activity is not complete

AT_RISK
    ↓
activity is not yet objectively delayed
BUT
multiple deterministic warning signals indicate meaningful schedule risk

AHEAD
    ↓
healthy positive variance

ON_TRACK
    ↓
neither ahead nor at risk nor delayed
```

This is a core Pass 12 architectural requirement.

# 6. Deterministic rule hierarchy

Implement an explicit rule hierarchy rather than arbitrary scoring.

Recommended priority:

```text id="9v8m6f"
1. COMPLETED
2. DELAYED
3. AT_RISK
4. AHEAD
5. ON_TRACK
```

Why?

An activity that is already completed should not simultaneously be reported as overdue/risk.

An activity whose planned finish has passed and remains incomplete should be `DELAYED`, even if its progress variance happens to be small due to the baseline model.

An activity still inside its planned window can be `AT_RISK`.

---

# 7. COMPLETED

Classify:

```text id="3b6r5p"
COMPLETED
```

when:

```text
status === 'completed'
OR
actualProgress >= 100
```

Use deterministic canonical progress data from Pass 11.

Do not require actualFinish to be non-null if the canonical status/progress already indicates completion.

A completed activity cannot simultaneously be:

```text id="n3y6rv"
DELAYED
AT_RISK
AHEAD
ON_TRACK
```

for its primary Pass 12 classification.

---

# 8. DELAYED

Classify:

```text id="8f7a0k"
DELAYED
```

when:

```text
asOfDate > plannedFinish
AND
actualProgress < 100
```

This intentionally reuses the objective overdue invariant from Pass 11.

Do not redefine overdue differently in Pass 12.

The rationale should make the condition explicit, for example:

```text
"Planned finish date has passed while actual progress remains below 100%."
```

The activity's Pass 11 `overdue = true` is therefore a strong deterministic signal.

---

# 9. AT_RISK

This is the main new logic.

An activity may be `AT_RISK` even before the planned finish date has passed.

Use transparent deterministic signals such as:

### Signal A — meaningful negative variance

For example:

```text
progressVariance <= -10 percentage points
```

or another clearly documented threshold.

Recommended initial threshold:

```text
<= -10.0 → risk signal
```

Do not make the threshold configurable unless the existing project configuration architecture supports it.

### Signal B — approaching planned finish

Define a milestone/proximity window.

Recommended:

```text
snapshotDate >= plannedFinish - 3 calendar days
AND
snapshotDate < plannedFinish
```

This is a warning signal, not automatic risk by itself.

### Signal C — significant variance near finish

A particularly strong combination is:

```text
near planned finish
AND
behind plan
```

This should produce `AT_RISK` even if the variance is smaller than the standalone threshold.

For example:

```text
planned progress = 90
actual progress = 82
variance = -8
2 days remain
```

→ `AT_RISK`.

### Signal D — delayed execution status

If Pass 11 status is:

```text
delayed
```

the activity should be `AT_RISK` unless it is already objectively overdue, in which case `DELAYED` wins.

---

# 10. Do not over-trigger AT_RISK

A single weak signal should not necessarily trigger risk.

Use a simple deterministic policy.

Recommended:

```text id="w5e3q7"
AT_RISK if:

(
  strongNegativeVariance
)
OR
(
  nearFinish AND behindPlan
)
OR
(
  status === delayed
)
```

where:

```text
strongNegativeVariance:
    progressVariance <= -10

behindPlan:
    varianceState === 'behind'

nearFinish:
    0 <= daysUntilPlannedFinish <= 3
```

Do not trigger risk merely because:

```text
daysUntilFinish <= 3
```

by itself.

An activity that is 100% complete naturally near its finish should already be `COMPLETED`.

---

# 11. AHEAD

Classify:

```text id="j3m8x4"
AHEAD
```

when:

```text
progressVariance > 0.01
```

and none of the higher-priority states apply.

A completed activity remains:

```text
COMPLETED
```

even if it has positive variance.

---

# 12. ON_TRACK

Anything not classified as:

```text id="m3u7q9"
COMPLETED
DELAYED
AT_RISK
AHEAD
```

becomes:

```text id="w8k2c4"
ON_TRACK
```

This gives us an exhaustive classification.

Never return an undefined risk state.

---

# 13. Milestone proximity

The earlier roadmap specifically mentions milestone proximity.

The current model does not appear to have a dedicated milestone entity.

Therefore, use the existing schedule boundaries conservatively.

A schedule activity with:

```text plannedStart === plannedFinish
```

is effectively a zero-duration milestone under Pass 11 semantics.

For such activities:

```text before milestone date
    → plannedProgress = 0

on/after milestone date
    → plannedProgress = 100
```

Pass 12 should respect that existing semantics.

Do not invent a separate milestone database model.

For non-zero-duration activities, use the finish-date proximity window:

```text 3 calendar days
```

as the deterministic "approaching finish" signal.

# 14. Risk rationale

Every Pass 12 classification should be explainable.

Return a concise machine-readable set of reasons.

Recommended:

```ts id="g7k2m4"
{
  code:
    | 'completed'
    | 'overdue'
    | 'strong_negative_variance'
    | 'near_finish_and_behind'
    | 'delayed_status'
    | 'positive_variance'
    | 'within_plan';

  message: string;
}
```

An activity may have multiple risk signals even though it receives one primary classification.

Example:

```json id="b2q5z8"
{
  "classification": "AT_RISK",
  "reasons": [
    {
      "code": "near_finish_and_behind",
      "message": "Activity is within 3 days of planned finish and remains behind planned progress."
    }
  ]
}
```

Do not generate natural-language explanations using an LLM.

You are now implementing **Phase 4 — Notification Persistence, Idempotency & Retry Reliability** for FieldLine.

Phase 1 and Phase 2 established anomaly detection and channel-neutral anomaly explanation.

Phase 3 established immediate HTTP email delivery through Resend.

Phase 4 must now transform that into a **durable, idempotent, retryable notification system** without redesigning the anomaly or email architecture.

The core principle remains:

```text
ML detects.
Groq explains.
Notification system records intent.
Delivery adapters deliver.
```

# 1. CORE OBJECTIVE

Change the notification model from:

```text
anomaly
  ↓
generate message
  ↓
send email immediately
```

to:

```text
anomaly
  ↓
persist anomaly
  ↓
atomically create notification intent
  ↓
notification worker
  ↓
generate/reuse Phase 2 message
  ↓
deliver via email adapter
  ↓
success / retry / permanent failure
```

The important distinction is:

**Phase 4 persists the intent to notify; the delivery adapter performs the external side effect.**

---

# 2. DO NOT REUSE `processing_jobs` UNLESS THE AUDIT PROVES IT IS CLEARLY APPROPRIATE

The current repository already has:

```text
processing_jobs
```

but it is currently explicitly designed for asynchronous processing jobs and its schema restricts `job_type` to:

```text
document_ingestion
```

with:

```text
queued → processing → completed | failed
```

and generic job fields.

Do not automatically overload this table for notification delivery.

Prefer a dedicated:

```text
notification_outbox
```

unless the actual current architecture makes a unified job model materially cleaner without weakening notification semantics.

The notification system requires concepts such as:

* notification event identity
* channel
* idempotency key
* next retry time
* delivery status
* provider message ID
* retryable vs permanent failure
* immutable payload snapshot

Do not distort the existing document-processing job model merely to avoid creating a table.

# 4. ATOMICALLY CREATE THE OUTBOX WITH THE ANOMALY RECORD

This is a mandatory invariant.

The transaction should conceptually be:

```text
BEGIN
    persist anomaly/activity match
    create notification_outbox row
COMMIT
```

Then, only after commit:

```text
notification worker → external delivery
```

Never perform the Resend HTTP request inside the SQLite transaction.

The objective is to eliminate this failure mode:

```text
anomaly committed
server crashes
notification intent never recorded
```

The outbox row must be created as part of the same successful persistence unit as the anomaly when the anomaly qualifies for notification.

# 5. DO NOT CREATE NOTIFICATIONS FOR NORMAL/COLD-START

Preserve the existing Phase 1/2 policy:

```text
normal → no notification
cold start → no notification
```

Only eligible anomaly severities should create an outbox record.

Do not create a pending notification and later decide it was unnecessary.

# 6. ENFORCE LOGICAL IDEMPOTENCY IN SQLITE

The same anomaly event must not create multiple logical notification records for the same channel.

Define a deterministic identity conceptually equivalent to:

```text
anomaly-alert:<activityMatchId>:email
```

or another repository-appropriate event key.

Prefer a database uniqueness constraint/index protecting the logical event.

For example, conceptually:

```text
(project_id, activity_match_id, notification_type, channel)
```

must be unique where appropriate.

Do not rely solely on Resend idempotency.

The application itself should know:

> "This anomaly already has an email notification intent."

# 7. PRESERVE A SNAPSHOT OF THE PHASE 2 MESSAGE PAYLOAD

Do NOT make notification retries call Groq again.

The preferred lifecycle is:

```text
anomaly persisted
    ↓
create notification intent
    ↓
generate Phase 2 AnomalyAlertMessage exactly once
    ↓
store immutable message/payload snapshot
    ↓
email delivery
```

or, if the current Phase 3 architecture already generates the message before the outbox transaction, ensure the equivalent immutable payload is captured in the outbox.

The crucial invariant is:

```text
One notification event
    ↓
One message snapshot
    ↓
All delivery retries reuse that exact payload
```

This is important both for consistency and for Resend idempotency.

Do not regenerate natural-language content on every retry.

# 10. SAFE CLAIMING / LEASE SEMANTICS

A notification must be atomically claimed before delivery.

The worker should transition:

```text
pending/retry_wait
        ↓
processing
```

and set:

```text
locked_at
```

or an equivalent lease timestamp.

Another worker must not simultaneously claim the same row.

Follow the existing `JobRepository.claimNextQueued()` transactional pattern where appropriate.

---

# 11. RECOVER STALE NOTIFICATIONS

If the process crashes after claiming:

```text
processing
```

but before completion:

```text
locked_at = old
```

the next worker startup/poll should be able to identify the stale lease and return the notification to a retryable state.

Use a bounded lease timeout.

Do not create an infinite retry loop.

---

# 12. RETRY CLASSIFICATION

Classify delivery errors into two categories.

### Retryable

At minimum consider:

```text
HTTP 429
HTTP 500
HTTP 502
HTTP 503
HTTP 504
network failures
connection reset
timeout
temporary provider failures
```

### Permanent

At minimum consider:

```text
HTTP 400
HTTP 401
HTTP 403
invalid request
invalid sender
invalid recipient
missing/invalid configuration
```

Do not retry permanent configuration/authentication failures indefinitely.

Use the actual Resend response semantics already present in the Phase 3 adapter.

---

# 13. RETRY BACKOFF

Implement a bounded backoff policy.

A simple sequence such as:

```text
attempt 1 → short delay
attempt 2 → longer delay
attempt 3 → longer again
...
```

is sufficient.

For example:

```text
1m
5m
15m
30m
```

The exact values may follow repository conventions, but must be:

* bounded
* non-zero
* increasing
* testable
* capped

Add small jitter if useful and simple.

Do not busy-loop.

---

# 14. MAXIMUM ATTEMPTS

Set an explicit maximum number of delivery attempts.

After the limit:

```text
status = failed
```

with a machine-readable error code and human-readable sanitized summary.

Do not retry forever.

The exact limit can be chosen after inspecting current configuration conventions.

Prefer configuration or a clearly documented constant over scattering the value through worker code.

---

# 15. RESEND IDEMPOTENCY

Preserve the Phase 3 Resend idempotency-key behavior.

The key must remain deterministic for the same notification event.

Resend's API supports idempotency keys and uses them to suppress duplicate processing of the same email request. Its documentation also states that retries using the same idempotency key should use the same payload; otherwise the provider can reject the request as an invalid idempotent request.

Therefore:

```text
same notification
    ↓
same idempotency key
    ↓
same email payload
```

must remain true across retries.

Do not generate a new random key per retry.

---

# 16. HANDLE THE "CRASH AFTER SEND, BEFORE DB UPDATE" CASE

This is a critical failure scenario.

Example:

```text
worker
  ↓
Resend accepts email
  ↓
process crashes
  ↓
notification row still says processing
```

When the stale row is retried, FieldLine may make the same request again.

This is exactly where the deterministic Resend idempotency key protects against duplicate delivery.

The architecture must explicitly account for this scenario.

Add a behavioral test for it where practical.

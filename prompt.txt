# 1. Objective

Build the deterministic information/query layer that a future assistant and dashboard can use.

The intelligence layer must answer:

```text
What is delayed?

What is at risk?

What was completed today?

Which activities are behind schedule?

Which milestones are approaching?

Which activities have no recent updates?

What changed recently?
```

The output must be **structured facts**, not generated prose.

The assistant layer comes later.

---

# 2. Core architectural principle

Do NOT create a new truth model.

Pass 17 is a READ/QUERY layer over existing canonical data.

Architecture:

```text
HTTP
 ↓
IntelligenceQueryService
 ↓
existing repositories / deterministic services
 ↓
structured intelligence response
```

Reuse the existing:

```text
ProgressSnapshotService
RiskClassificationService
ActivityProgressRepository
ProgressUpdateRepository
ActivityRepository
ProjectEventRepository
Evidence/provenance services where useful
```

Do NOT duplicate progress, variance, overdue, or risk formulas.

# 3. Existing canonical sources

## 3.1 Progress snapshot

The existing:

```text
GET /api/projects/:projectId/progress-snapshot
```

returns deterministic planned-vs-actual information and accepts an optional `asOfDate`.

The snapshot service:

* validates `asOfDate`
* gets project activities
* retrieves latest ActivityProgress as of that date
* calculates planned progress
* calculates actual progress
* calculates variance
* calculates overdue
* returns a project summary

Reuse these semantics. Do NOT reimplement them.

The existing calculator defines:

```text
plannedProgress
actualProgress
progressVariance
varianceState
overdue
```

with deterministic rules.

---

# 4. Canonical intelligence endpoint

Create:

```text
GET /api/projects/:projectId/intelligence
```

This is the canonical Pass 17 read surface.

Query parameters:

```text
asOfDate        optional YYYY-MM-DD
recentDays      optional positive integer
approachingDays optional non-negative integer
```

Recommended defaults:

```text
recentDays = 7
approachingDays = 14
```

Make these configurable constants, not magic numbers scattered across the code.

Do not accept arbitrary natural-language questions yet.

Do NOT create an LLM query interpreter.

# 8. Behind-schedule activities


Do not calculate a second notion of "behind".

```text

```

```text

```

# 9. Completed today

Define "today" as:

```text
asOfDate
```

not the server wall clock.

Return activities with a canonical ActivityProgress observation representing completion on the requested date.

Prefer:

```text
status === 'completed'
```

with:

```text

```

or an explicitly defensible equivalent based on the existing historical model.

Do NOT treat:

```text

Job.completedAt
```

as activity completion.

The source of truth is ActivityProgress.

Include:

```text
activityId
externalId
name

```

# 10. Approaching milestones

The existing snapshot calculator defines a milestone as a zero-duration activity:

```text
plannedStart === plannedFinish
```

Use that definition.

Return milestones satisfying:

```text
plannedStart >= asOfDate
plannedStart <= asOfDate + approachingDays
```

Do not use calendar time-of-day.

Use canonical `YYYY-MM-DD` semantics.

Include:

```text
activityId
externalId
name
milestoneDate
daysUntil
status
actualProgress
```

Sort ascending by:

```text
milestoneDate
externalId
```

for deterministic output.

Do not include already-past milestones in the approaching list.

---

# 11. Activities with no recent updates

Define a stale activity using ActivityProgress history.

For each project activity:

```text
latest progress observation as of asOfDate
```

If no historical ActivityProgress exists:

```text
stale = true
```

Otherwise:

```text
stale = latestObservation.asOfDate < asOfDate - recentDays
```

Use calendar-date arithmetic consistent with the repository's existing date-normalization logic.

Do NOT use:

```text
new Date() - updatedAt
```

because historical queries must remain deterministic.

Return:

```text
activityId
externalId
name
latestUpdateDate
daysSinceUpdate
hasAnyUpdate
```

where:

```text
latestUpdateDate = null
```

when no update exists.

Sort oldest/no-update first.

---

# 12. Recent changes

Use `project_events`.

Add a project-scoped event query if the repository does not already provide one.

Conceptually:

```text
GET recent events
WHERE project_id = ?
AND created_at <= now/asOfDate boundary
ORDER BY created_at DESC
LIMIT bounded number
```

However, historical determinism matters.

When `asOfDate` is supplied, recent changes should be bounded relative to that date rather than silently using today's timestamp.

A practical contract is:

```text
asOfDate = YYYY-MM-DD

recentChanges = events on or before the end of asOfDate
within a configurable recent event window
```

If event timestamps are UTC ISO strings, normalize the date boundary carefully.

Do not make natural-language summaries.

Return:

```json
{
  "eventId": "...",
  "eventType": "progress_updated",
  "entityType": "activity_progress",
  "entityId": "...",
  "summary": "...",
  "createdAt": "...",
  "payload": {...}
}
```

Use existing event payloads.

Do not expose absolute filesystem paths or internal error stacks if an event contains such data.

# 13. Determinism

The same database state plus the same query parameters must produce the same logical result.

Be explicit about:

```text
sorting
date boundaries
limits
default parameters
null behavior
```

Do not rely on unspecified SQLite row order.

Every array must have a deterministic ORDER BY.

# 14. Project isolation

Every query must be project-scoped.

Examples:

```text id="iso17"
Project A intelligence must never include Project B activities.

Project A recent events must not include Project B events.

Project A stale activity analysis must only inspect Project A progress.

Cross-project projectId/activity/event identifiers must return no foreign data.
```

Follow existing project isolation conventions.

Do not introduce globally unscoped intelligence queries.

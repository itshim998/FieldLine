# FieldLine — PASS 20: PRIMARY PROJECT DASHBOARD

Implement **Pass 20 — Dashboard** in the existing FieldLine repository.

Approved base is the current `main` after Pass 19.

Before editing, inspect the actual repository HEAD and current implementation.

Do NOT implement Pass 21+.

---

# 1. Objective

Build the primary presentation interface so a manager/judge can understand the project's current state within seconds.

The dashboard must show:

```text id="obj20"
Project health
Activity status
Recent updates
Milestones
Evidence/provenance
Review uncertainty where relevant
```

The dashboard is a PRESENTATION layer.

It must NOT become a second source of project truth.

---

# 2. Existing canonical sources

Reuse the existing APIs/services.

Important existing sources include:

```text id="sources20a"
ProgressSnapshotService
RiskClassificationService
ProjectIntelligenceService
ProgressUpdateRepository / APIs
ActivityMatch / review APIs
Evidence APIs
```

The existing Project Intelligence endpoint is:

```http
GET /api/projects/:projectId/intelligence
```

and already exposes:

```text id="7facts20"
delayed
atRisk
completedToday
behindSchedule
approachingMilestones
staleActivities
recentChanges
```

Reuse it.

Do NOT recreate these calculations in React.

Do NOT introduce separate formulas for risk, variance, delay, milestone timing or staleness.

---

# 3. Dashboard architecture

Preferred architecture:

```text id="arch20"
Existing canonical data
      ↓
Dashboard composition
      ↓
Presentation components
```

Do NOT make the dashboard itself responsible for domain truth.

Do NOT create:

```text id="nobiz20"
new risk engine
new progress engine
new milestone engine
new stale-update engine
new matching engine
```

---

# 4. Decide whether a dashboard endpoint is necessary

First inspect current frontend API usage.

Preferred:

```text id="api20a"
reuse existing endpoints
```

If the dashboard requires too many separate project-scoped HTTP requests and a thin aggregation endpoint materially improves correctness/performance, add:

```http
GET /api/projects/:projectId/dashboard
```

but ONLY as a composition endpoint.

Its implementation may call/reuse existing domain services.

It must NOT duplicate business rules.

If added, define typed response DTOs and project isolation.

---

# 5. Dashboard response

The dashboard needs a compact project overview.

Conceptually:

```ts id="dashdto20"
interface ProjectDashboard {
  project: ProjectSummary;
  health: ProjectHealthSummary;
  activityStatus: ActivityStatusSummary;
  recentUpdates: DashboardRecentUpdate[];
  milestones: DashboardMilestoneSection;
  attention: DashboardAttentionSummary;
}
```

Reuse existing DTOs where practical.

Do not duplicate the entire project database model.

---

# 6. Project Health section

Top-of-dashboard section:

```text id="health20"
Project Health
```

Show:

```text
Overall Progress
Planned Progress
Variance
Health / Risk Classification
```

Use the existing progress snapshot and risk classification.

Example:

```text
62% Actual
74% Planned
-12 pts
AT RISK
```

Do NOT invent another score such as:

```text
Health = 73
```

unless that metric already exists in the repository.

Use canonical terminology.

---

# 7. Activity Status section

Display counts for:

```text id="status20"
ON_TRACK
AHEAD
AT_RISK
DELAYED
COMPLETED
```

Use the existing deterministic risk classification output.

Do not recalculate the classifications in frontend code.

Clicking a status should allow navigation/filtering to the relevant existing activity/progress view.

Do not create the future Activity Detail View in this pass.

---

# 8. Attention summary

Create a compact "Needs Attention" section using existing facts:

```text id="attention20"
Delayed: N
At Risk: N
Stale Updates: N
Unresolved Matches: N
```

Use:

```text id="6mrssx"
ProjectIntelligence.delayed
ProjectIntelligence.atRisk
ProjectIntelligence.staleActivities
```

For unresolved matches, use existing Pass 19 review-state data.

Do not invent another attention/risk score.

Clicking an item should navigate to the existing relevant workspace/view.

---

# 9. Recent Updates

Create a chronological dashboard section:

```text id="recent20"
Recent Updates
```

Each item should show at minimum:

```text
date/time
activity
reported progress/status
source
```

Source examples:

```text
manual
xlsx
pdf
image
text
voice
```

Use canonical ProgressUpdate and ActivityProgress data.

Do NOT infer activity completion from:

```text
Evidence.uploadedAt
job.completedAt
frontend timestamp
```

Activity progress remains authoritative.

---

# 10. Recent update ordering

Use deterministic ordering.

Newest first.

Tie-break deterministically when timestamps are equal.

Do not rely on arbitrary SQLite row order.

Use bounded results.

A reasonable default is:

```text id="recentlimit20"
10 most recent meaningful updates
```

or another clearly documented limit consistent with existing APIs.

Do not load unlimited history into the dashboard.

---

# 11. Milestones section

Show:

```text id="milestone20"
Upcoming Milestones
```

and:

```text
Recently Completed / Late Milestones
```

Use the same milestone definition already used by Project Intelligence:

```text id="milestone_definition20"
plannedStart === plannedFinish
```

Do not create another milestone calculation.

For upcoming milestones, reuse:

```text id="reusemilestone20"
ProjectIntelligence.approachingMilestones
```

with an appropriate UI limit.

---

# 12. Completed / late milestones

For completed milestones, inspect existing ActivityProgress / risk data.

A milestone should not be called "completed" merely because its date passed.

Use canonical ActivityProgress status / actual finish where available.

For a late milestone, use existing authoritative progress/risk fields.

Do NOT create a new late-milestone formula.

If the current repository cannot establish "completed late" unambiguously, expose only what the canonical data supports rather than guessing.

---

# 13. Evidence-backed navigation

The dashboard should allow users to get to the source evidence behind a result.

For update/activity cards where provenance exists, provide:

```text id="evidence20"
View Evidence
```

or:

```text
Trace Evidence
```

Use existing Evidence APIs and identifiers.

Do NOT display filesystem paths.

Do NOT duplicate Evidence storage.

Do NOT build a second Evidence inventory.

The existing Evidence workspace remains authoritative for full evidence management.

---

# 14. Progress update click behavior

Clicking a recent update should navigate/open the existing progress history/review surface.

Where match review is applicable:

```text
Confirmed
Suggested
Unresolved
Rejected
```

must remain visually distinguishable.

Do not create new review semantics in the dashboard.

---

# 15. Review uncertainty on dashboard

Surface unresolved work clearly.

For example:

```text
Needs Review
Foundation B
Medium confidence — Suggested

Unresolved
"North wall"
Low confidence — Unresolved
```

Do NOT present suggested/unresolved matches as normal canonical progress.

Only confirmed matches represent canonical truth.

This is inherited directly from Pass 19.


# 21. As-of date

Because Project Intelligence already supports deterministic:

```text id="asof20"
asOfDate
```

the dashboard should clearly display the date represented by its metrics.

Example:

```text
As of 28 Aug 2026
```

Do not make the dashboard imply that historical metrics are today's values.

If the current dashboard is live/today-oriented, use today's canonical snapshot date.

A date selector is optional; do not add one unless it fits naturally with the existing Project Intelligence controls.

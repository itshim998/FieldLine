PASS 24 — Golden Demo Environment
Objective

Create a fully deterministic, presentation-ready local FieldLine environment for SIH 2026.

The goal is not merely “insert sample data.”

The goal is:

Run one command and get the exact project state needed for the SIH demonstration, every single time.

The environment must be:

reset
↓
seed
↓
start FieldLine
↓
same project
↓
same schedules
↓
same evidence
↓
same progress history
↓
same dashboard
↓
same activity detail
↓
same intelligence
↓
same assistant answers

No manual database editing should be necessary.

1. Golden demo project

Use a realistic flagship project:

Refinery Expansion — Unit 4

This is preferable to simply copying the smaller Pass 23 “Metro Transit Hub” project because Pass 24 is a presentation dataset, not a regression fixture.

Target roughly 30 activities.

The activities should be distributed across multiple work areas, for example:

Area A — Civil / Earthworks
Area B — Foundation
Area C — Structural
Area D — Piping
Area E — Electrical / Instrumentation
Area F — Commissioning

Do not create six completely artificial disconnected groups. They should feel like one real infrastructure/industrial project.

2. Dataset composition

The 30-or-so activities should deliberately produce a useful dashboard state.

Include:

Category	Approximate target
On track	12–16
Behind / mildly negative variance	4–6
At risk	3–4
Delayed / overdue	2–4
Completed	3–5
Milestones	3–5
Stale / no recent update	several

These are targets, not rigid counts.

The final distribution must be driven by the actual risk/progress engine so the dashboard tells a coherent story.

Do not manually label an activity “AT_RISK” or “DELAYED” in the database if those values are derived by existing engines.

3. Realistic schedule data

Create a canonical demo schedule containing:

activity IDs
activity names
WBS codes
work areas
planned start/finish
planned quantities
units
baseline progress where supported by the current schema

The data should resemble a real EPC/infrastructure schedule rather than a toy dataset.

Example activity naming style:

Unit 4 Site Grading
North Tank Foundation Excavation
Crude Pump Foundation Piling
Pipe Rack PR-07 Structural Erection
Cooling Water Header Installation
Process Pipe Rack Carbon Steel Spooling
Electrical Substation Civil Works
MCC Room Cable Tray Installation
Instrument Air Header Testing
Unit 4 Hydrotest Package A

Use the actual schedule import/normalization path where practical so the demo data remains representative of real user input.

4. Messy field reports

This is the most important presentation feature.

Create realistic human-written field reports containing multiple ways of describing the same scheduled activity.

For example, for one canonical activity such as:

ACT-014 — Block B Excavation

the evidence can contain:

“Block B excavation roughly 65% done.”

Another report:

“Excavation at B is practically finished.”

Another:

“Section B earthwork completed.”

The point is to visually demonstrate that FieldLine can connect heterogeneous field language to canonical schedule activities.

Do this across several activities, not only one.

Use multiple linguistic variations:

shortened names
location-first descriptions
informal site language
spelling/casing variation
quantity-oriented descriptions
completion phrases
partially specified descriptions

Do not fabricate activity IDs inside these human-written reports unless that is intentionally part of a test scenario.

5. Multiple report dates

Do not make the demo consist of one report on one day.

Create a small history, for example:

D-14
D-10
D-7
D-3
D-1
D0 / presentation date

The exact dates should be deterministic.

This allows the demo to show:

changing progress
historical observations
overdue activities
completed work
recent updates
stale activities
asOfDate behavior

This is especially important because Pass 23 established historical/deterministic evaluation as a major invariant.

6. Canonical progress history

Seed actual ActivityProgress only through the repository's canonical mechanisms.

Do not directly insert fake canonical progress rows merely for convenience unless the existing data-seeding architecture absolutely requires it.

The final dataset should contain a believable progression history.

For example:

Foundation excavation:
20% → 38% → 52% → 65%

Pipe rack erection:
15% → 31% → 48%

Electrical room:
0% → 12% → 26%

Tank foundation:
100% completed

The exact values should be selected so the existing snapshot/risk calculations generate a visually meaningful state.

7. Evidence files

Seed a realistic evidence set.

Prefer actual local files over database-only placeholders.

Include several:

.txt
.csv
.pdf where practical
optionally a small image/photo fixture if the existing application path supports it cleanly

Examples:

daily_site_report_2026-08-18.txt
civil_progress_update_2026-08-21.csv
weekly_execution_report_2026-08-24.pdf
inspection_note_unit4.txt
piping_progress_2026-08-27.csv

These should live inside the existing local upload/evidence model.

Do not put secrets or unnecessary large binary assets in Git.

Keep fixtures small and repository-friendly.

8. Matches and review states

The golden environment should intentionally contain all useful review situations.

Include:

Clearly resolved

Some reports should produce strong, unambiguous matches.

Suggested

Some observations should remain pending review.

Rejected

At least one deliberately incorrect candidate should be rejected.

Manually resolved

At least one ambiguous observation should demonstrate the human review path.

This is important for the demo because it shows the human-in-the-loop model rather than portraying AI as automatically authoritative.

The current repository already encodes this review model:

confirmed → canonical eligible
suggested → awaiting review
rejected → non-canonical
resolved → confirmed via human action

and Pass 23 tests these boundaries.

9. Assistant-ready state

The final dataset must produce meaningful answers to questions such as:

What is delayed?

Which activities are at risk?

What changed recently?

What is behind schedule?

What happened in Area B?

Tell me about the tank foundation.

The assistant must answer from the actual seeded project state, not from hardcoded demo responses.

Do not add a “demo mode” that bypasses the existing grounded assistant.

10. Dashboard-ready state

The seeded project should make the dashboard visually useful immediately.

It should contain enough variation to produce:

meaningful overall progress
a non-zero variance
delayed activities
at-risk activities
completed activities
upcoming milestones
stale activities
recent updates
evidence-linked updates

The dashboard should therefore tell a story at first load.

11. Activity Detail-ready state

At least 3–5 activities should have especially rich histories.

For those activities, the Activity Detail screen should show:

Identity
↓
Current state
↓
Progress timeline
↓
Source report
↓
Match/review history
↓
Originating evidence

This is where Pass 21 + Pass 24 should meet.

Do not add new Activity Detail functionality in this pass.

Just create the dataset that makes the existing feature compelling.

12. Deterministic seed architecture

Create a proper demo seeding layer.

For example:

scripts/
    demo-reset.ts
    demo-seed.ts

demo/
    golden-demo.ts
    fixtures/
        schedules/
        reports/
        evidence/

You may choose better names based on the existing architecture.

The essential requirement is that the dataset has one canonical source definition.

Do not scatter dozens of unrelated INSERT statements through demo-reset.ts.

Prefer a structured deterministic seed definition that can be consumed by a small seed orchestrator.

13. Redesign npm run demo:reset

The existing demo:reset currently resets to an empty database.

Change its semantic meaning to:

npm run demo:reset

=

remove previous runtime state
↓
recreate database
↓
run migrations
↓
seed golden project
↓
seed schedules
↓
seed progress history
↓
seed evidence
↓
seed matches/review state
↓
verify canonical state
↓
verify dashboard/intelligence
↓
verify assistant-ready state
↓
exit

After it completes, running:

npm run dev

must immediately show the golden demo environment.

14. Demo reset must be idempotent

Running:

npm run demo:reset
npm run demo:reset
npm run demo:reset

must always result in the same logical project state.

No duplicate:

projects
schedules
activities
evidence
progress updates
matches
events

should accumulate.

15. Golden demo verification

Do not trust the seeder merely because it exits with code 0.

Add a dedicated verification step/test.

For example:

npm run demo:verify

or an appropriate equivalent.

It should verify at minimum:

Project

Exactly one canonical golden demo project exists.

Schedule

Expected schedule(s) exist with expected activity count.

Progress

Expected canonical observations exist.

Risk

Expected counts/classifications are produced by the real risk engine.

Intelligence

Expected delayed/at-risk/completed/milestone/stale outputs are produced.

Dashboard

Expected headline numbers appear.

Assistant

A deterministic assistant query returns grounded facts matching the seeded state.

Evidence

Expected evidence records/files exist.

16. Golden dataset should have machine-verifiable invariants

Create a small manifest containing expected logical values.

For example:

projectCode
activityCount
scheduleCount
expectedDelayedIds
expectedAtRiskIds
expectedCompletedIds
expectedMilestoneIds
expectedStaleIds
expectedProgressSummary

Do not duplicate production logic here.

The manifest should contain expected results, not calculation formulas.

17. Demo fixture determinism

Use fixed:

project code
activity IDs
report dates
file names
textual evidence
progress percentages
reviewer names where relevant

Avoid:

Date.now()
Math.random()
current system date
random UUIDs in semantic assertions

Generated database UUIDs may remain generated internally, but the logical golden dataset must be stable.

18. Demo seed should not depend on Gemini

This is critical.

npm run demo:reset must work offline.

The golden presentation environment should not require:

Gemini API calls
internet access
external services
Docker
cloud databases

Use the existing deterministic/local AI machinery where AI-generated extraction must be represented.

The repo is explicitly designed as a local-only presentation environment.

19. Do not contaminate production architecture

This pass must not introduce:

special demo-only database tables
alternate domain calculations
a separate demo dashboard
fake assistant APIs
hardcoded frontend values
demo-only production branches scattered across services
bypasses around review/canonical-truth rules

The demo dataset must operate through the same application paths used by normal FieldLine behavior.

20. Documentation

Update the relevant documentation so that a fresh clone can understand:

npm install
npm run setup
npm run demo:reset
npm run dev

and immediately reproduce the SIH demo.

Update:

README
implementation plan / roadmap as appropriate
demo instructions if a dedicated document is created

The README currently states that npm run demo:reset resets to a pristine state, so that description must be corrected to reflect the new golden-demo semantics.

21. Verification commands

At the end of the pass, run:

npm run demo:reset
npm run demo:verify
npm test
npm run build

All must pass.

Then verify manually that:

npm run dev

opens directly into the populated golden project.

22. Exit criteria

Pass 24 is complete when:

Reset
npm run demo:reset

recreates the exact golden environment.

Reproducibility

Running reset repeatedly yields the same logical state.

Dataset

A realistic industrial project exists with roughly 30 activities across multiple work areas.

Progress story

The project includes believable historical progress and a mixture of completed, on-track, at-risk, delayed, and stale activities.

Messy language

Multiple differently worded field observations map to the same canonical scheduled activities.

Human review

Suggested, rejected, and manually resolved match states are represented.

Evidence

The project contains realistic locally stored evidence connected to reports/progress.

Dashboard

The dashboard opens with a meaningful, presentation-ready state.

Activity Detail

Several activities have useful execution histories.

Intelligence

The intelligence endpoint produces deterministic, meaningful results.

Assistant

The assistant answers from the actual seeded project state and remains grounded.

Offline

The demo can be rebuilt without Gemini or external services.

Regression

Existing tests/build continue to pass.

Verification

A machine-checkable golden-demo verification exists.

This pass is:

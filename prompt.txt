# CRITICAL ISSUE 1 — POSTGRES MIGRATIONS ARE BEING STARTED TWICE

Inspect:

```text
backend/src/database/provider.ts
backend/src/database/postgres.ts
backend/src/database/postgres-migrator.ts
backend/src/index.ts
```

Current behavior is effectively:

```text
startServer()
  ↓
initActiveDatabase()
  ↓
initPostgres()
  ↓
runPostgresMigrations()

THEN

startServer()
  ↓
runPostgresMigrations()
```

`initPostgres()` already runs migrations, while `startServer()` invokes `runPostgresMigrations()` again.

Additionally, `initActiveDatabase()` currently does not await `initPostgres()`.

This creates the observed race:

```text
migration runner A
+
migration runner B
        ↓
both see baseline migration as pending
        ↓
duplicate schema_migrations.name
```

Observed production error:

```text
duplicate key value violates unique constraint "schema_migrations_name_key"
```

### Required fix

There must be exactly ONE authoritative PostgreSQL migration execution during startup.

Choose the cleanest existing architecture and make startup deterministic.

Requirements:

```text
✓ initPostgres is awaited
✓ migration runs exactly once
✓ no concurrent migration runners
✓ existing SQLite startup behavior remains intact
✓ existing migration semantics remain intact
✓ PostgreSQL startup still verifies/applies pending migrations
```

Do not merely catch/suppress the duplicate-key error.

Fix the race itself.

Add a regression test proving that startup initialization does not launch two migration runs concurrently.

```text

```

followed by:

```text

null value in column "project_id" of relation "schedules" violates not-null constraint
```

I inspected the current code.

`demo/golden-demo-seeder.ts` calls:


without `await`.

The SQLite repository interface returns:

```text

```


The current Proxy-based repository selector allows a PostgreSQL async implementation to be exposed through a repository interface that is typed as synchronous.

This is an unsafe abstraction.

Perform a repository-wide audit of the dual SQLite/PostgreSQL provider system.

Search for all repository/service calls where:

```text
SQLite implementation = synchronous
PostgreSQL implementation = asynchronous
```

and verify that callers correctly support both engines.

Do NOT patch only `getByCode()`.

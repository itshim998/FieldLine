# BLOCKER 1 — Implement real scanned-PDF OCR

Current `PdfExtractor` detects sparse/no embedded text and invokes `OcrExtractor` with the original PDF buffer.

That is not a valid PDF OCR pipeline.

Current conceptual behavior:

```text
PDF bytes
↓
Tesseract OCR
```

This must become:

```text
scanned PDF
↓
render PDF page(s) to raster image(s)
↓
OCR each rendered page
↓
combine page OCR text in deterministic page order
↓
NormalizedDocument
```

## Requirements

For a valid PDF with little/no usable embedded text:

1. determine the pages that need OCR
2. render those pages to images using a local Node-compatible implementation
3. OCR the rendered images
4. preserve page ordering
5. bound page count and output length
6. normalize OCR output
7. return:

```text
sourceType = 'pdf'
metadata.fallbackMethod = 'ocr'
```

Do not pass raw PDF bytes directly into Tesseract.

The OCR engine abstraction may remain:

```ts
interface OcrEngine {
  recognize(imageBuffer: Buffer): Promise<{
    text: string;
    confidence?: number;
  }>;
}
```

That abstraction should receive actual image bytes.

## PDF parse fallback

Currently PDF parsing errors immediately become:

```text
ValidationError("Failed to parse PDF...")
```

Do not prevent the OCR path merely because embedded text extraction failed.

Separate these conditions:

```text
PDF structurally unreadable
vs
PDF structurally readable but contains little/no embedded text
```

For a structurally valid scanned PDF, OCR must be reachable.

Do not hide genuinely corrupt PDFs.

## Tests

Add a realistic scanned-PDF regression using a real or generated PDF fixture whose pages contain raster text.

The test must prove:

```text
PDF
↓
rendered page image
↓
OCR
↓
non-empty normalized text
```

Do not satisfy this test merely by mocking OCR against raw PDF bytes.

Retain existing embedded-text PDF tests.

# BLOCKER 2 — Do not persist ProgressUpdate before the processing workflow is valid

Current sequence:

```text
extract document
↓
create ProgressUpdate
↓
attach evidence
↓
AI extraction
```

is unsafe.

AI extraction failure can leave a persistent ProgressUpdate behind.

Change the workflow so failed document processing does not leave a partially-created progress capture.

Required conceptual sequence:

```text
1. validate project/evidence
2. extract document
3. validate normalized text
4. AI field extraction
5. persist ProgressUpdate
6. attach evidence
7. run ActivityMatchingService
8. return result
```

However, preserve the existing downstream architecture and ensure persistence is failure-safe.

If persistence of the ProgressUpdate + evidence association needs transaction support, use the existing repository/database transaction conventions.

Do not create a second persistence model.

# BLOCKER 3 — Evidence provenance failure MUST NOT be swallowed

Current code does:

```ts
try {
  attachToProgressUpdate(...)
} catch {
  logger.warn(...)
}
```

This is unacceptable.

A successful document-processing operation must guarantee:

```text
Evidence.progressUpdateId = created ProgressUpdate
```

If attachment fails:

```text
processing must fail
```

Do not continue and do not return success.

Do not merely log the error.

The originating Evidence must remain the authoritative source artifact.

Add a regression test:

```text
evidence
+
successful extraction
+
simulated attach failure
```

Expected result:

```text
processing fails
no successful processing response
no silently orphaned ProgressUpdate
```

If a ProgressUpdate was already created before the attachment failure, it must be rolled back/deleted as part of the failure-safe transaction.

Do not leave partial state.

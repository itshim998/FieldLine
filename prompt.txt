# Persistence architecture

Preserve this dependency direction:

```text
Service
   ↓
Repository interface
   ↓
SQLite repository implementation
   ↓
Database connection
   ↓
SQLite
```

The service layer should depend on repository interfaces.

The repository implementation owns SQL.

The database module owns SQLite connection lifecycle and low-level database configuration.

No route should contain SQL.

No service should contain SQL.

No AI code should contain SQL.

# Migrations

Do not continue using one giant hard-coded schema string as the long-term database strategy.

Introduce a small deterministic migration mechanism appropriate for the project.

Requirements:

* migrations are ordered;
* migrations are tracked in SQLite;
* running setup repeatedly is safe;
* already-applied migrations are not re-run incorrectly;
* a fresh database reaches the current schema deterministically;
* migrations can be added in later passes.

A simple custom migration runner is preferable to introducing an ORM or heavy migration framework.

Do not introduce Prisma, TypeORM, Drizzle, Sequelize, or another ORM.

The project intentionally uses lightweight SQLite.

# Transaction support

Introduce transaction support at the repository/database boundary.

The goal is not to build a transaction framework.

The goal is to establish that related writes can be performed atomically.

Provide a lightweight transaction helper or repository-level transaction mechanism appropriate for `better-sqlite3`.

Demonstrate it with a meaningful test.

For example:

```text
transaction starts
    ↓
write succeeds
    ↓
commit
```

and:

```text
transaction starts
    ↓
write fails
    ↓
rollback
```

A failed transaction must not leave partially committed state.

Keep the API simple.

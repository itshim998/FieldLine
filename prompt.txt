# PASS 10 Corrective Fix — Preserve Historical `actualFinish`

Pass 10 is **not yet approved**.

The current implementation correctly preserves the earliest historical `actualStart`, but it does **not** apply the same historical reconciliation to `actualFinish`.

The problem is in:

```text id="f8u9p1"
backend/src/services/progress/progress.service.ts
```

The current flow effectively does:

```ts
const finalActualFinish = normalized.actualFinish;
```

So a later-arriving completed report can overwrite the historical completion date.

Example:

```text id="xgj1wi"
Report A
asOfDate = 2026-08-20
status = completed
→ actualFinish = 2026-08-20

Report B
asOfDate = 2026-08-26
status = completed
→ current code produces actualFinish = 2026-08-26
```

That is incorrect for FieldLine's append-only historical observation model.

---

# Required Fix

## 1. Preserve the earliest established `actualFinish`

Mirror the existing `actualStart` reconciliation logic.

Before persisting the new observation:

1. Load existing `activity_progress` history for the activity.
2. Collect all non-null `actualFinish` values.
3. Determine the earliest historical finish date.
4. If a historical finish exists, preserve it rather than replacing it with a later date.

Conceptually:

```ts id="9m6d2e"
let finalActualFinish = normalized.actualFinish;

const historicalFinishDates = history
  .map(r => r.actualFinish)
  .filter((d): d is string => d !== null && d !== undefined && d.length > 0)
  .sort();

if (historicalFinishDates.length > 0) {
  const earliestHistoricalFinish = historicalFinishDates[0];

  if (finalActualFinish) {
    finalActualFinish =
      earliestHistoricalFinish < finalActualFinish
        ? earliestHistoricalFinish
        : finalActualFinish;
  } else {
    finalActualFinish = earliestHistoricalFinish;
  }
}
```

Use the same deterministic date representation already used elsewhere in the repository.

Do not introduce a new date abstraction unless the current codebase requires it.

# 2. Preserve historical truth, not processing order

The key rule is:

```text id="h2h2p0"
asOfDate determines chronology
not insertion time
not processing time
```

Example:

```text id="x6s4bq"
Observation A:
asOfDate = 2026-08-20
actualFinish = 2026-08-20

Observation B:
asOfDate = 2026-08-26
actualFinish = 2026-08-26
```

The second observation must preserve:

```text id="7e6kl4"

```

because the activity was already observed as completed earlier.

Also test the reverse arrival order:

```text id="2fb4qg"

then insert 2026-08-20 observation
```

The historical result must still resolve correctly according to `asOfDate`.

# 1. Objective

Add natural-language interaction to FieldLine.

A manager should be able to ask:

```text
What is delayed?

Why is Foundation B at risk?

What changed today?

Which activities are most behind schedule?

Which milestones are approaching?

Which activities have no recent updates?
```

and receive an answer grounded strictly in actual project data.

Required architecture:

```text id="arch18"
Manager question
      ↓
AI structured intent interpretation
      ↓
application validation
      ↓
deterministic project/entity resolution
      ↓
ProjectIntelligenceService
      ↓
verified structured fact set
      ↓
AI structured answer generation
      ↓
validated grounded answer
```

The LLM is NEVER the source of project truth.

---

# 2. Critical architectural rule

DO NOT let the assistant query:

* SQLite
* repositories
* filesystem

The architecture must remain:

```text id="truth18"

      ↓

      ↓
Project Intelligence
      ↓
Assistant
```

not:

```text
LLM
 ↓

```

# 7. Intent interpretation

Create:

```text id="intentservice18"
AssistantIntentService
```

that calls:

```text
AIService.extractStructured(...)
```

with the intent schema.

Prompt the model to:

* classify only into supported intents
* extract an optional human activity reference
* extract an optional explicit date
* never invent activity IDs
* never answer the question
* never calculate project values

Example:

```text
Question:
"Why is Foundation B at risk?"

Expected intent:

{
  "intent": "at_risk",
  "activityQuery": "Foundation B",
  "explicitDate": null
}
```

Another:

```text
"Which activities are most behind schedule?"

{
  "intent": "behind_schedule",
  "activityQuery": null,
  "explicitDate": null
}
```

Another:

```text
"What changed on 2026-08-25?"

{
  "intent": "recent_changes",
  "activityQuery": null,
  "explicitDate": "2026-08-25"
}
```

Invalid intent output must fail validation.

# 8. Application-controlled date semantics

Do not trust the LLM with relative dates.

If the user asks:

```text
today
```

the application determines the canonical date using existing snapshot/date semantics.

If the LLM returns:

```text
explicitDate
```

validate it using the same date validation conventions already used by the ProgressSnapshotService.

Do not invent dates.

Do not use Evidence.uploadedAt or job timestamps for semantic project dates.

# 9. Deterministic activity resolution

Create a small deterministic resolver.

Input:

```text
projectId
activityQuery
```

Resolve against:

```text
ActivityRepository.listByProjectId(projectId)
```

Use deterministic matching only.

Preferred resolution precedence:

```text id="resolve18"
1. exact externalId
2. exact case-insensitive normalized activity name
3. exact normalized name + location
4. unique deterministic textual match
```

Normalization may include:

* trim
* lowercase
* collapse whitespace

Do not use an LLM for entity resolution.

Do not invent an Activity ID.

If no match:

```text id="nomatch18"
return a safe "activity not found" assistant result
```

If multiple equally valid matches:

```text id="ambiguous18"
do not guess
return an ambiguity result containing the candidate activities
```

Do not silently choose one.

```ts
  factRefs: string[];
}
```

Use:


```text

```

Keep the answer concise enough for a manager UI.

---

# 14. Grounding enforcement

The final answer prompt must state:

```text id="ground18"
You are not the source of truth.

The VERIFIED FACTS below are the only project facts available.

You must:
- answer only from VERIFIED FACTS
- preserve numeric values exactly
- preserve dates exactly
- preserve activity identity exactly
- cite factual claims with factRefs

You must not:
- invent project facts
- invent percentages
- invent dates
- invent causes
- invent activities
- infer unsupported contractor/personnel issues
- perform new project calculations
- contradict VERIFIED FACTS

If the VERIFIED FACTS are insufficient:
say that the available project data is insufficient.

Every factual statement in the answer must be supported by one or more supplied factRefs.
```

The model receives:

```text
original question
+
resolved intent
+
verified fact set
```

and nothing else from the project.

---

# 15. Validate returned fact references

After the LLM response:

```text id="factcheck18"
answer.factRefs
```

must be checked against the application-generated verified fact set.

If the model returns an unknown reference:

```text id="badref18"
do not accept the answer
```

Return a safe assistant error or regenerate once using the same verified facts.

Do NOT silently accept unsupported references.

Prefer deterministic rejection over hallucination.

# 19. Assistant API

Add:

```text id="assistantroute18"
POST /api/projects/:projectId/assistant/query
```

Request:

```json
{
  "question": "Why is Foundation B at risk?"
}
```

Optional:

```json
{
  "question": "...",
  "asOfDate": "2026-08-28"
}
```

The application may use `asOfDate` as an explicit user/UI override, but must validate it.

Response conceptually:

```json
{
  "question": "Why is Foundation B at risk?",
  "intent": {
    "type": "at_risk",
    "activityQuery": "Foundation B",
    "explicitDate": null
  },
  "answer": "Foundation B is at risk because ...",
  "factRefs": [
    "activity-risk:ACT-123"
  ],
  "grounded": true,
  "asOfDate": "2026-08-28"
}
```

Exact contract may be refined consistently with existing API conventions.

Do not expose raw LLM provider internals.

# 21. Insufficient data

If the question is valid but the verified data is insufficient:

```text
grounded = false
```

or an equivalent explicit status.

Example:

```text
"What changed on 2025-01-01?"
```

when no relevant events exist.

The assistant should say that the available project data does not contain the requested information.

Do not fill the gap from general model knowledge.

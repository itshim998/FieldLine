# PASS 1 scope

Implement the architectural skeleton for the application.

The following concerns must exist with clear boundaries:

### Application configuration

Create or formalize a central configuration boundary.

The application should not read `process.env` arbitrarily throughout the codebase.

Prefer:

```text
process.env
    ↓
validated configuration
    ↓
application code
```

Keep Zod validation at the configuration boundary.

Do not introduce a complicated configuration framework.

---

# HTTP route layer

Routes should remain thin.

A route should primarily perform:

```text
HTTP request
    ↓
request validation
    ↓
service invocation
    ↓
HTTP response
```

Routes should **not**:

* execute SQL directly;
* contain domain calculations;
* contain business rules;
* call an AI SDK directly;
* perform large orchestration logic.

The current health route should be refactored where necessary to follow this architectural direction without changing its externally observable behavior unnecessarily.

---

# Request validation

Create a clean validation boundary.

Use Zod for request/input validation.

The architecture should make it easy for future routes to define:

```text
Request
    ↓
Zod schema
    ↓
validated input
    ↓
service
```

Avoid duplicating validation logic inside services.

Do not create domain schemas for projects, schedules, activities, progress, etc. yet.

Those belong to later passes.

---

# Service layer

Create a clear application/service layer.

Services should own orchestration and business operations.

For this pass, use a small representative service where useful to prove the boundary.

The health endpoint may be used as the architectural example, but do not invent fake business behavior merely to populate the service directory.

A service should **not** directly depend on Express request/response objects.

Prefer:

```text
route
  → service input
  → service result
  → route response
```

rather than passing HTTP objects into the service.

---

# Repository abstraction

Create a repository/data-access boundary.

The repository layer owns direct SQLite access.

The architectural dependency should be:

```text
route
   ↓
service
   ↓
repository
   ↓
SQLite
```

Services must not embed SQL.

Routes must not embed SQL.

AI code must not embed SQL.

The repository abstraction should be designed so later passes can add repositories such as:

```text
projectRepository
scheduleRepository
activityRepository
progressRepository
evidenceRepository
...
```

Do **not** implement those future domain repositories now.

Create only what is necessary to prove the architectural pattern.

A small system/health-oriented repository is sufficient for this pass if it allows the architecture to be genuinely exercised.

---

# Database boundary

Keep the existing SQLite connection management where it is working.

Do not replace the local SQLite strategy.

The database layer should remain responsible for:

* opening the database;
* connection lifecycle;
* SQLite pragmas;
* low-level database access;
* schema initialization that already belongs to Pass 0.

Repositories should use the database layer rather than reaching into SQLite configuration themselves.

Do not implement the full domain schema in this pass.

That belongs to PASS 2.

# AI architecture skeleton

This pass must establish the **shape** of the future AI architecture without implementing FieldLine's actual AI features.

Create the boundary:

```text
AI service
    ↓
AI adapter
    ↓
structured response
    ↓
validation
    ↓
service
```

The purpose is architectural decoupling.

For example, create conceptual interfaces/types along the lines of:

```text
AIProvider
AIRequest
AIResponse
Structured AI contract
```

but adapt the names and structure to the actual repository conventions.

The important properties are:

### AI service

Owns application-level orchestration around an AI capability.

It should not know provider-specific SDK details.

### AI adapter

Owns communication with a specific provider.

It should be replaceable later.

For example, later we may have:

```text
OpenAI adapter
Gemini adapter
Mock adapter
```

but **do not implement multiple real providers now**.

A mock/in-memory adapter may be used if necessary to demonstrate the architectural boundary and test it.

### Structured response

AI responses must have an explicit application contract.

Use Zod to validate the response before the service accepts it.

The architecture should therefore make this sequence possible:

```text
provider returns unknown data
        ↓
adapter translates provider response
        ↓
structured application response
        ↓
Zod validation
        ↓
service receives trusted structure
```

Do not let arbitrary provider response objects flow directly into application logic.

---

# Important AI restriction

Do **not** let the AI layer:

* query SQLite;
* import repository modules;
* modify project state;
* write directly to the database;
* calculate project truth;
* contain FieldLine business rules.

The architectural separation must remain:

```text
AI
→ interpretation / structured extraction

Application services
→ validation / orchestration / business rules

Repositories
→ persistence

SQLite
→ storage
```

This distinction is one of FieldLine's core non-negotiable principles.

# Error handling

Formalize a clean application error boundary.

The current centralized error middleware may already exist.

Inspect it first.

Improve/refactor only where necessary so that:

* application errors are distinguishable from unexpected errors;
* validation errors have a stable response shape;
* routes/services do not repeat response formatting logic unnecessarily;
* database errors do not leak internal implementation details;
* unexpected errors are logged appropriately.

Do not create an elaborate enterprise error framework.

Keep it small.

# Architectural testability

Prefer dependency boundaries that are testable.


Do not over-engineer this.

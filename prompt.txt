Backend implementation
1. Project service

Create a ProjectService boundary over the existing repository.

The service should provide the application-level operations needed by Pass 3, such as:

createProject
listProjects
getProject
updateProject
deleteProject

Use explicit typed inputs and outputs.

The service must not depend on Express Request or Response.

The service must not contain SQL.

Use the existing repository abstraction.

Do not add a generic service framework.

2. Request validation

Create Zod schemas for project API inputs.

At minimum validate:

Create project
name
code
description
status
startDate
targetEndDate
Update project

Only fields that are actually editable.

Project ID

Validate the route parameter.

Use sensible constraints, for example:

name required and non-empty;
code required and non-empty;
description optional;
status constrained to existing ProjectStatus;
dates represented consistently with the repository/database conventions.

Do not introduce overly complex date/business validation yet.

3. HTTP API

Create a project router.

Use a clean REST-style API.

Suggested endpoints:

GET    /api/projects
POST   /api/projects
GET    /api/projects/:projectId
PATCH  /api/projects/:projectId
DELETE /api/projects/:projectId

Use the existing project service.

Routes should be thin.

Do not put SQL or business logic inside routes.

4. Response contracts

Define explicit Zod schemas/types for the API response shapes where appropriate.

At minimum:

Project
ProjectList

Keep the API responses predictable.

For example:

{
  "project": { ... }
}

for a single project and:

{
  "projects": [ ... ]
}

for the collection.

Use whatever exact response convention best matches the current repository, but remain consistent across endpoints.

5. Error behavior

Use the existing AppError architecture.

Expected cases:

Create

Duplicate project code → conflict response.

Get/open

Unknown project ID → not-found response.

Update

Unknown project ID → not-found response.

Duplicate replacement code → conflict response.

Delete

Unknown project ID should have a predictable behavior.

Do not expose raw SQLite implementation details to the browser.

Use the existing centralized error handler.

6. Project event

Consider whether creating/updating/deleting a project should create an appropriate project_events record.

Because the project_events table already exists from Pass 2, an event such as:

project_created
project_updated
project_deleted

would fit the current data model.

However, do not build a general event framework.

A simple service-level implementation is enough if you use events.

If deletion makes event persistence impossible because the project is cascaded away, do not invent complicated audit behavior. Keep the deletion semantics simple and document the choice.

The goal is project lifecycle, not audit architecture.

Do not add a complex recycle-bin system.

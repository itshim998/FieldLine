# 1. REQUIRED ROUTING SEMANTICS

The intended behavior remains:

```text
Current Key
    ↓
keep using Current Key
    ↓
successful requests
    ↓
Current Key remains unchanged
```

When the current key fails:

```text
Current Key fails
    ↓
immediately advance
    ↓
try next configured key
    ↓
success
    ↓
new successful key becomes Current Key
```

Subsequent requests must remain on that successful key until it fails.

This is NOT request-count round robin.

Correct:

```text
01 → 01 → 01 → 01
01 fails
02 → 02 → 02
02 fails
03 → 03 → 03
```

Incorrect:

```text
01
02
03
04
...
```

---

# 2. BLOCKING RACE CONDITION

The current implementation does:

```ts
recordFailure(failedKey)
    → currentKeyIndex = nextKey

recordSuccess(successfulKey)
    → currentKeyIndex = successfulKey
```

This is not sufficient when two requests are concurrently in flight.

Example:

```text
Initial current = 01

Request A starts using 01
Request B starts using 01

A → 01 fails
    → router moves current to 02

B → 01 succeeds later
    → current is changed back to 01
```

That is WRONG.

Once a newer router transition has moved the active state from 01 to 02, a stale success from an older request that was already operating on 01 must NOT revert the router to 01.

Expected:

```text
A → 01 fails
A → 02 succeeds

B → stale 01 success arrives later

Final current key MUST remain 02
```

The latest valid routing state must not be overwritten by an older in-flight request.

---

# 3. FIX THE STATE-TRANSITION SEMANTICS

Inspect the current `GroqKeyRouter` implementation and introduce the smallest correct mechanism needed to make state transitions concurrency-safe.

A good implementation may use a generation/epoch/version associated with the active routing state, for example:

```text
routingEpoch
```

or an equivalent mechanism.

The conceptual invariant is:

```text
state transition N
    ↓
only operations associated with the current/latest routing state
    may mutate the active sticky key
```

An older in-flight request must be allowed to finish, but its eventual success/failure must not incorrectly roll back a newer routing decision.

Do NOT simply serialize every request globally unless the repository architecture genuinely requires it.

The desired behavior is still:

* requests can execute concurrently
* provider I/O remains asynchronous/concurrent
* only the sticky routing state transition needs protection

# 5. IMPORTANT: STALE SUCCESS RULE

Explicitly encode this rule:

> A success from an older request may count toward that key's health statistics, but it must not overwrite a newer active-key routing decision.

For example:

```text
Request A starts on 01
Request B starts on 01

A fails → active routing moves to 02
B succeeds on stale 01

Allowed:
01.successCount++

Not allowed:
currentKeyIndex = 01
```

This distinction is important.

Do not discard useful health information merely because the request became stale for routing purposes.

---

# 6. IMPORTANT: STALE FAILURE RULE

Likewise inspect stale failures.

Example:

```text
Current = 01

A starts on 01
B starts on 01

A fails
→ current moves to 02

B later fails on stale 01
```

That stale failure must update Key 01 health appropriately, but must NOT perform an additional active-key transition based on an already superseded state.

Do not accidentally make:

```text
02 → 01
```

or skip forward unexpectedly because of the stale operation.

The active routing cursor must reflect the newest legitimate routing transition.

# 10. ALSO FIX THE ENVIRONMENT EDGE CASE

While this correction is open, fix the small configuration inconsistency identified during review.

Current `extractGroqApiKeys()` treats an explicitly present empty numbered variable as malformed.

That means:

```env

```

The intended configuration should allow:

* one configured Groq key

* all 20 configured Groq keys

* a key variable that is present but contains whitespace/empty content should not be treated as a configured credential
* malformed actual credential values should still be rejected according to the repository's validation policy
* if `AI_PROVIDER=groq` and zero usable keys exist, startup must fail clearly

Add/update environment tests for:

```text

all 20 keys
empty unused slots
no usable keys
```

Preserve numeric ordering.

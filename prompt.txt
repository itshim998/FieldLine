The first correction introduced `routingEpoch`, which successfully protects the active sticky cursor from stale concurrent completions.

However, the router still has a second concurrency problem:

> **A stale in-flight request can mutate a key's authoritative health state after a newer request has already established a newer health state.**

This is the only target of this correction.

Do NOT redesign Pass 26.
Do NOT change the AIProvider abstraction.
Do NOT change the 20-key routing model.
Do NOT change the intended sticky/failover behavior.

Make a minimal correctness fix.

---

# 1. THE REQUIRED INVARIANT

There are two distinct pieces of router state:

```text
A. Active routing state
B. Per-key health state
```

Both must be protected against stale asynchronous completions.

The existing `routingEpoch` currently protects A.

This correction must protect B as well.

---

# 2. THE REMAINING BUG

The current `recordSuccess()` effectively does:

```text
successCount++
failureCount = 0
lastSuccessAt = now
cooldownUntil = null
lastErrorStatus = null

then:
check whether attemptEpoch is stale
```

That ordering is unsafe.

Likewise, `recordFailure()` mutates:

```text
failureCount
lastFailureAt
lastErrorStatus
cooldownUntil
isPermanentlyInvalid
```

before deciding whether the completion is stale.

Therefore a stale completion can overwrite newer state.

---

# 3. FAILURE SCENARIO A — STALE SUCCESS RESURRECTS A FAILED KEY

Reproduce this exact sequence deterministically:

```text id="1lq8hh"
Initial current key = 01

Request A starts on Key 01
Request A is slow

Request B starts on Key 01
Request B fails with HTTP 429

Key 01:
    failureCount = 1
    cooldownUntil = future
Current key advances to 02

Request A finally succeeds on old Key 01
```

### REQUIRED RESULT

The stale success may be counted only if the implementation intentionally treats it as diagnostic data.

But it MUST NOT:

```text id="d9fe93"
failureCount = 0
cooldownUntil = null
lastErrorStatus = null
```

when those values represent newer state established by Request B.

Most importantly:

```text id="m0th0g"
Key 01 must remain unhealthy/cooling down
Current key must remain 02
```

The stale success must not resurrect Key 01.

---

# 4. FAILURE SCENARIO B — STALE FAILURE POISONS A NEWLY HEALTHY KEY

Reproduce:

```text id="vya4di"
Request A starts on Key 01
Request A is slow

A newer request establishes a valid healthy state for Key 01

Request A eventually fails
```

The stale failure must NOT overwrite the newer healthy state by doing:

```text id="s1q4ea"
failureCount++
cooldownUntil = future
lastErrorStatus = ...
```

The newer state must win.

---

# 5. REQUIRED DESIGN

Use a monotonic state version/generation for each key, or an equivalent concurrency-safe mechanism.

For example:

```ts id="h52qj4"
interface KeyHealthState {
    ...
    healthEpoch: number;
}
```

At the moment an attempt is dispatched, capture the relevant health-state version:

```text id="rj5ofm"
attemptHealthEpoch
```

When a health mutation happens:

```text id="1xk2be"
only apply it if the attempt still corresponds to the latest state
```

A stale completion must not overwrite a newer health state.

The exact implementation is up to you.

Do NOT blindly copy this example if a better mechanism fits the current code.

---

# 6. IMPORTANT DISTINCTION: HEALTH EVENTS VS ROUTING EVENTS

Do not conflate:

```text id="b1a5ew"
routingEpoch
```

with:

```text id="2lqxgz"
keyHealthEpoch
```

They represent different things.

`routingEpoch` answers:

> Is this request still allowed to mutate the active sticky cursor?

`keyHealthEpoch` answers:

> Is this request still allowed to overwrite the key's latest health state?

Preserve both invariants.

---

# 7. REQUIRED RULE FOR STALE SUCCESS

If a success arrives with a stale health epoch:

```text id="8hfzjd"
do NOT overwrite newer health state
```

In particular, do not clear:

* newer cooldown
* newer permanent invalid state
* newer failure count
* newer lastErrorStatus

The safest default is:

```text id="x8ocg4"
stale success
→ record optional diagnostic-only information
→ do not mutate authoritative health state
```

If you decide to retain a success counter for stale completions, make sure that counter cannot accidentally make a newer failed key appear healthy.

Prefer correctness over unnecessary statistics.

---

# 8. REQUIRED RULE FOR STALE FAILURE

If a failure arrives with a stale health epoch:

```text id="0n4grf"
do NOT overwrite newer health state
```

Do not:

* add a newer cooldown
* change a newer `lastErrorStatus`
* increment the authoritative failure sequence
* mark a key permanently invalid based only on a stale completion

Again, diagnostic logging is acceptable.

---

# 9. PERMANENT INVALID STATE

Be especially careful with:

```text id="g4o9v4"
401 / 403
→ isPermanentlyInvalid = true
```

A stale success must NEVER resurrect a key that a newer request has established as permanently invalid.

For example:

```text id="rznv04"
01 request A starts

01 request B → 401
01 becomes permanently invalid

A later succeeds

01 must remain permanently invalid
```

Add an explicit regression test.

---

# 10. COOLDOWN STATE

Likewise:

```text id="4j2xkq"
newer 429
→ cooldownUntil = T

older success
→ must NOT clear cooldownUntil
```

And:

```text id="r0r1me"
newer success
→ clears a previous cooldown appropriately

older failure
→ must NOT reintroduce the old cooldown
```

These two directions must both be tested.

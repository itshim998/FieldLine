# PASS 10 — Progress Normalization

You are implementing **FieldLine PASS 10 — Progress Normalization**.

Passes 0–9 are complete and approved.

Your first task is to inspect the current repository on `main` and implement Pass 10 around the architecture that actually exists today.

Do not assume the original roadmap maps perfectly onto the current repository.

---

# 1. Current architectural state

FieldLine currently has:

```text
Raw field report
      ↓
PASS 8 — AI Extraction
      ↓
structured field facts
      ↓
PASS 9 — Activity Matching
      ↓
activity match / scheduled activity identity
```

Pass 10 now converts those facts into canonical activity execution progress.

The target pipeline is:

```text
Pass 8 structured fact
        ↓
Pass 9 activity identity
        ↓
Progress Normalization
        ↓
canonical ActivityProgress
        ↓
SQLite activity_progress
```

The architectural principle is:

> Pass 10 is deterministic domain normalization. It must not ask an LLM to calculate project progress.

# 3. Pass 10 objective

Convert structured progress facts into canonical actual progress.

Support these forms:

### Percentage

```text
60% complete
```

→

```text
actualPercent = 60
```

### Quantity

```text
300 m³ completed
```

combined with:

```text
plannedQuantity = 500 m³
```

→

```text
actualQuantity = 300
actualPercent = 60
```

### Status

Support canonical execution status:

```text
not_started
started
in_progress
completed
delayed
```

The existing Pass 8 extraction status enum is:

```text
unknown
not_started
in_progress
completed
delayed
```

Map it deterministically into the existing ActivityExecutionStatus enum.

For example:

```text
unknown      → no forced execution status unless another deterministic signal exists
not_started  → not_started
in_progress  → in_progress
completed    → completed
delayed      → delayed
```

`started` is available in `ActivityExecutionStatus` even though Pass 8 does not explicitly emit it. Use it only where deterministic normalization from the available evidence justifies it.

# 4. Core rule — quantity-derived percentage

This is one of the most important rules in Pass 10.

When both:

```text
actualQuantity
plannedQuantity
```

are available and valid:

```text
actualPercent =
  actualQuantity / plannedQuantity * 100
```

Do this in normal application code.

Do NOT:

* ask an LLM to calculate it
* trust an LLM-supplied percentage when deterministic quantity data exists
* use floating-point garbage outside 0–100
* silently ignore contradictory quantities

Example:

```text
plannedQuantity = 500 m3
actualQuantity  = 300 m3

actualPercent = 60
```

Use a deterministic rounding policy and document it.

Recommended:

```text
round to 2 decimal places
```

Example:

```text
233 / 500 * 100 = 46.6
```

---

# 5. Percentage precedence

Define and document a deterministic precedence order.

Recommended:

```text
1. Quantity-derived percentage
2. Explicit reported percentage
3. Completion status fallback
4. No safe percentage
```

Meaning:

### Case A

```text
planned = 500
actual = 300
reported = 50%
```

Canonical result:

```text
actualQuantity = 300
actualPercent = 60
```

because deterministic quantity math is authoritative.

### Case B

```text
plannedQuantity unavailable
reported = 60%
```

Canonical result:

```text
actualPercent = 60
```

### Case C

```text
plannedQuantity unavailable
actualQuantity unavailable
status = completed
```

Canonical result may be:

```text
actualPercent = 100
status = completed
```

because completed is a deterministic canonical state.

### Case D

```text
plannedQuantity unavailable
actualQuantity unavailable
status = in_progress
```

Do NOT invent a percentage.

The normalization result should indicate that no numeric percentage could safely be derived.

---

# 6. Never exceed 100%

If quantity math produces:

```text
actualQuantity > plannedQuantity
```

do NOT silently invent another scale.

Use deterministic policy.

Recommended:

```text
actualPercent = min(100, calculatedPercent)
```

but retain the actual quantity.

Example:

```text
planned = 500 m3
actual = 550 m3

actualQuantity = 550
actualPercent = 100
```

Also preserve an explanatory note such as:

```text
"Quantity-derived progress exceeded 100%; actual percent was capped at 100."
```

Do not silently throw away the overrun.

This preserves useful physical quantity evidence while respecting the ActivityProgress percentage invariant.

---

# 7. Units matter

Do not divide:

```text
300 m3
```

by:

```text
500 tonnes
```

and call the result 60%.

Only derive a quantity-based percentage when the units are compatible.

Use the existing schedule `unit` field.

The normalization logic must compare normalized unit strings conservatively.

Examples:

```text
m3
m³
```

should be treated as equivalent if the existing normalization utilities already support that representation.

But:

```text
m3
tonnes
```

must not be treated as compatible.

Do not invent unit conversions in Pass 10.

Do not introduce a full unit-conversion engine.

If units are incompatible:

```text
quantity-derived percentage unavailable
```

and fall back to explicit percentage if one exists.

Pass 8 currently outputs only:

```text

```

There is intentionally no quantity field in the current extraction contract.

Therefore, do NOT redesign Pass 8 casually.

Instead inspect how Pass 10 should obtain quantity information from the current repository architecture.

The safest initial implementation is:

```text

+

```

alongside the already validated Pass 8 fact.

For example:

```json

    "progress_percent": null,
    "status": "in_progress"
  },
  "activity": {
    "...matched activity identity..."
  },
  "actualQuantity": 300,
  "quantityUnit": "m3"
}
```

Do not use an LLM inside Pass 10 to convert arbitrary prose into quantity unless the current repository clearly demonstrates a safe established mechanism for it.

Quantity extraction from raw prose belongs to a future refinement of the extraction layer.

The key Pass 10 capability is **normalization**, not another AI extraction pass.

# 10. Which match statuses may feed Progress Normalization?

This boundary must be explicit.

Do NOT automatically convert a `rejected` match into actual activity progress.

Recommended policy:

```text
confirmed
    → allowed

suggested
    → allowed only if explicitly requested by the caller for deterministic demo/workflow use

rejected
    → rejected
```

Prefer the safest default:

```text
only confirmed matches mutate ActivityProgress
```

However, the current project does not yet appear to have a full human-review confirmation workflow.

Therefore:

* design the service so match status is checked
* make `confirmed` the safe production default
* provide a clearly named option for demo/test usage of a `suggested` match, if necessary
* never silently treat `rejected` as valid
* never automatically change a match from suggested → confirmed

Do not build the full Pass 19 review system now.

# 13. Handling `actualPercent` being NOT NULL

The current SQLite schema requires:

```text
actual_percent NOT NULL
```

Therefore Pass 10 cannot persist a row when there is genuinely no safe numeric percentage.

Do NOT fabricate a percentage just to satisfy the schema.

Instead:

```text
normalization succeeds
→ numeric percentage unavailable
→ persistence rejected with a clear validation/domain error
```

Example:

```text
"Some foundation work continued."
```

with:

```text
status = in_progress
plannedQuantity = null
actualQuantity = null
progress_percent = null
```

must NOT become:

```text
actualPercent = 50
```

Instead return an explicit error such as:

```text
Cannot persist ActivityProgress because no deterministic actual percentage is available.
```

This is an important safety rule.

# 16. Determining the canonical latest observation

Use:

```text
asOfDate
createdAt
id
```

as deterministic ordering signals.

A later report should not be allowed to retroactively overwrite an earlier observation merely because it was processed later.

For example:

```text
Report A
asOfDate = 2026-08-20
actual = 40%

Report B
asOfDate = 2026-08-26
actual = 60%
```

latest canonical observation = 60%.

But:

```text
Report A
asOfDate = 2026-08-26
actual = 60%

Report B
asOfDate = 2026-08-20
actual = 40%
```

do not treat Report B as newer just because it was processed later.

# 17. Progress monotonicity

Do NOT silently enforce monotonic progress across all activities in Pass 10.

Construction projects can have corrections, rework, measurement corrections, or revised reporting.

Pass 10 should normalize each observation deterministically.

Do not reject:

```text
60% → 55%
```

merely because it decreased.

Later domain logic can determine whether that is a correction, rework, or anomaly.

# 19. Persistence must be atomic

The logical operation is:

```text
validate match
+
normalize progress
+
persist ActivityProgress
```

Do not perform unrelated mutations in this transaction.

If Pass 10 records a `progress_updated` project event, that event and the ActivityProgress insertion should be atomic just as Pass 7 established atomic persistence for manual progress reporting.

Do not swallow event failures.

If an event is added:

```text
activity_progress INSERT
+
progress_updated project_event INSERT
```

must be one transaction.

If event insertion fails:

```text
ROLLBACK BOTH
```

# 21. Duplicate/idempotency behavior

Think carefully about repeated requests.

A repeated normalization call for the **same match + same progress update + same asOfDate** should not create uncontrolled duplicate observations.

Implement deterministic behavior.

Recommended:

```text

+
same progressUpdateId
+
same activityId
+
same asOfDate
+
same normalized observation
```

→ return/reuse the existing observation rather than endlessly creating duplicates.

Do not introduce a database uniqueness constraint unless genuinely necessary.

Application-level deterministic lookup is acceptable for this pass, provided race-safety is considered.

# 1. Current architectural state

FieldLine now has this pipeline:

```text id="f1k8p2"
Raw field report
      ↓
PASS 8 — AI extraction
      ↓
structured field facts
      ↓
PASS 9 — Activity matching
      ↓
activity identity / suggested or reviewed match
      ↓
PASS 10 — Progress normalization
      ↓

```

Pass 11 must now answer:

> **"As of a specific date, what was planned to happen, what has actually happened, and what is the variance?"**

The target pipeline is:

```text id="t9d3q7"

        +
ActivityProgress history
        ↓
PASS 11 Planned vs Actual Engine
        ↓
read-only progress snapshot
        ↓
activity-level variance + project-level summary
```

Pass 11 is an **analytical/read-only layer**.

It must not modify project truth.

# 5. Planned progress calculation

The current schedule model provides planned start and finish dates but does not contain a full planned-progress curve.

Therefore, unless inspection of the current code reveals an already-established baseline curve, use this deterministic baseline model:

### Before planned start

```text id="0l4pdm"
asOfDate < plannedStart
→ plannedProgress = 0
```

### On or after planned finish

```text id="tj5rc8"
asOfDate >= plannedFinish
→ plannedProgress = 100
```

### During planned window

Use linear elapsed-duration progress:

```text id="z3x5kq"
plannedProgress =
  elapsedDays / plannedDurationDays * 100
```

Clamp to:

```text
0 <= plannedProgress <= 100
```

Example:

```text id="c7h2x1"
plannedStart  = 2026-08-01
plannedFinish = 2026-08-11
snapshot      = 2026-08-06

elapsed = 5 days
duration = 10 days

plannedProgress = 50%
```

### Date semantics

Use a single clearly documented convention for date arithmetic.

Prefer calendar-day arithmetic based on `YYYY-MM-DD` dates.

Do not use time-of-day or timezone-sensitive calculations for schedule dates.

Avoid off-by-one errors.

Test boundary dates explicitly.

# 7. Actual progress selection

For each activity and snapshot date:

Select the **latest ActivityProgress observation whose `asOfDate <= snapshotDate`**.

This is critical.

Do NOT simply use:

```text
getLatestByActivityId(activityId)
```

if that method may return a future-dated observation relative to the requested snapshot.

Pass 11 needs:

```text id="u9n7m3"
latest observation
WHERE as_of_date <= snapshotDate
ORDER BY as_of_date DESC,
         created_at DESC,
         id DESC
LIMIT 1
```

Add a repository method if necessary:

```ts id="0s9d3w"
getLatestByActivityIdAsOfDate(
  activityId: string,
  projectId: string,
  asOfDate: string
): ActivityProgress | null
```

Do not mutate the existing semantics of `getLatestByActivityId()`.

# 12. Overdue definition

Pass 11 needs an explicit, deterministic definition.

For this pass:

```text id="x5t7m2"
overdue =
  snapshotDate > plannedFinish
  AND actualProgress < 100
```

That means:

```text
planned finish passed
+
activity is not complete
=
overdue
```

Do NOT classify an activity as overdue merely because its actual progress is below planned progress while the planned finish date has not passed.

Example:

```text
planned progress = 60
actual progress = 40
snapshot = mid-schedule

→ behind plan
→ NOT overdue
```

This distinction is important.

Do not introduce Pass 12 risk scoring or delay detection yet.

---

# 13. Variance

For each activity:

```text id="q7r1s0"
progressVariance =
  actualProgress - plannedProgress
```

Round deterministically, preferably to 2 decimal places.

Example:

```text
planned = 60
actual = 40

variance = -20
```

Do not call this "delay" automatically.

Use neutral terminology:

```text
ahead
on_plan
behind
```

Optionally derive:

```ts id="m3r8f2"
varianceState:
  'ahead'
  | 'on_plan'
  | 'behind'
```

with a very small tolerance if justified.

Recommended exact policy:

```text id="t2j6k4"
variance > 0.01 → ahead
variance < -0.01 → behind
otherwise        → on_plan
```

Document the tolerance.

Do not overcomplicate this.

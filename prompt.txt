## PASS 9 — Activity Matching Engine

You are implementing **FieldLine PASS 9 — Activity Matching Engine**.

Pass 8 is complete and approved.

Your first task is to inspect the current repository carefully and implement Pass 9 around the architecture that actually exists today.

Do not assume the earlier roadmap maps 1:1 onto the current code.

---

# 1. Current architectural state

FieldLine now has this pipeline:

```text
Raw field report
      ↓
Pass 8 AI extraction
      ↓
validated structured field facts
```

Pass 8 produces:

```ts
{
  items: [
    {
      reference: string,
      location: string | null,
      progress_percent: number | null,
      status: 'unknown' | 'not_started' | 'in_progress' | 'completed' | 'delayed'
    }
  ]
}
```

The extracted `reference` is explicitly a **textual work reference**, NOT a schedule activity identity.

Pass 9 now has one responsibility:

> Take those structured field facts and identify the most likely scheduled activity or activities they refer to.

The central architectural principle remains:

```text
AI interprets messy evidence
        ↓
structured facts
        ↓
matching engine resolves activity identity
        ↓
later deterministic progress logic
```

Do not allow the AI layer to define project truth.

# 3. Pass 9 objective

Given:

```text
Project
+
validated field extraction
```

produce:

```text
candidate activity matches
```

with:

```text
matched activity
confidence
matching method
matching rationale
candidate alternatives
```

Example:

### Schedule

```text
ACT-101 | Foundation excavation | Block B | WBS 3.1
ACT-102 | Foundation concrete     | Block B | WBS 3.2
ACT-103 | Column rebar             | Block C | WBS 4.1
```

### Extracted field fact

```json
{
  "reference": "foundation work",
  "location": "Block B",
  "progress_percent": 60,
  "status": "in_progress"
}
```

Potential output:

```text
best match:
ACT-101
confidence: 0.87
method: text_similarity
rationale: "foundation" + "Block B" strongly align with activity name and location

alternatives:
ACT-102
confidence: 0.78
```

The matcher must not silently commit a low-confidence result as confirmed.

# 4. Match strategy

Implement a deterministic layered strategy.

Use this order:

```text
1. Exact activity/external ID
2. Strong text match
3. WBS/location metadata
4. Semantic similarity seam
5. LLM-assisted disambiguation seam
```

However, do NOT implement unnecessary advanced AI infrastructure merely because the roadmap mentions it.

The important Pass 9 result is the **matching contract and deterministic engine**.

Build the system so semantic/LLM methods can be added cleanly later.

---

# 5. Layer 1 — exact activity ID

First detect whether the extracted textual `reference` is actually an explicit activity identifier.

Example:

```text
ACT-001
ACT-001/A
A10023
```

Compare against `Activity.externalId`.

Rules:

* exact normalized match → strongest possible result
* confidence should be near 1.0
* `matchMethod = 'exact_id'`
* rationale should state that the external activity ID matched exactly

Use the existing normalization helpers where appropriate rather than inventing another identifier normalization implementation. The existing text normalizer preserves punctuation/case in identifiers.

Do not turn ordinary text like:

```text
"foundation work"
```

into a fabricated activity ID.

---

# 6. Layer 2 — strong text matching

Compare the extracted `reference` against:

```text
Activity.name
Activity.description
```

Do not use database-side fuzzy matching.

Keep the matching logic in a pure domain/application service.

Create a deterministic text similarity implementation.

It may use simple techniques such as:

```text
- normalized token comparison
- token overlap
- Jaccard similarity
- containment
- exact normalized phrase match
```

Do NOT introduce a heavyweight ML/embedding package in Pass 9 unless the existing project already contains one.

The goal is:

> deterministic, understandable matching first.

Example:

```text
reference:
"foundation excavation"

activity:
"Foundation Excavation at Block B"
```

should score strongly.

---

# 7. Layer 3 — WBS and location metadata

Use the extracted fact:

```text
location
```

and any schedule metadata available from activities:

```text
location
wbsCode
```

to strengthen or weaken candidate scores.

Examples:

```text
reference = foundation excavation
location = Block B
```

Candidate:

```text
Foundation Excavation
Block B
WBS 3.1
```

should score significantly higher than:

```text
Foundation Excavation
Block C
```

The matching engine should make the rationale explainable.

Example:

```text
"Reference strongly matches activity name; location also matches."
```

Do not make location mandatory because some field reports legitimately omit it.

---

# 8. Layer 4 — semantic similarity

Do NOT immediately introduce external embedding infrastructure.

Instead, design a clean interface/seam for semantic matching.

For example:

```ts
interface SemanticActivityMatcher {
  score(reference: string, activity: Activity): Promise<number>;
}
```

A deterministic/local implementation may return:

```text
0
```

or a text-based semantic proxy if useful.

The key requirement is architectural isolation:

```text
matching engine
      ↓
semantic matcher interface
```

rather than embedding provider logic directly into the core matcher.

If the current repo does not have a genuine semantic similarity dependency, do not add one merely for this pass.

---

# 9. Layer 5 — LLM-assisted disambiguation

Do not make the entire matcher dependent on an LLM.

Use the existing AI abstraction from Pass 8 only as an optional disambiguation layer.

The LLM must only be asked to choose among a **small set of already-qualified candidates**.

For example:

```text
Field fact:
"foundation work at Block B"

Candidates:
ACT-101 Foundation Excavation — Block B
ACT-102 Foundation Concrete — Block B
ACT-103 Column Rebar — Block C
```

The LLM may choose between the first two if deterministic scoring cannot safely distinguish them.

It must not:

* search the database
* invent candidate activities
* create activity IDs
* mutate activity matches
* decide project progress
* calculate variance
* calculate risk

Use the existing `AIProvider`/`AIService` abstraction.

If a clean LLM disambiguation implementation would materially expand the pass, create the abstraction and deterministic mock seam now, but keep production use optional.

---

# 10. Candidate ranking

The output of matching should preserve:

```text
best candidate
+
alternative candidates
```

Do not throw away runner-up information.

Recommended result structure:

```ts
{
  fact: FieldProgressItem,
  bestMatch: CandidateMatch | null,
  alternatives: CandidateMatch[]
}
```

Where:

```ts
CandidateMatch = {
  activityId: string,
  activityExternalId: string,
  activityName: string,
  confidenceScore: number,
  matchMethod: MatchMethod,
  matchedText: string | null,
  rationale: string
}
```

Confidence must always satisfy:

```text
0 <= confidenceScore <= 1
```

Use deterministic score calculations.

Document how the score is produced.

Do not pretend the score is mathematically calibrated probability.

It is a matching confidence score.

---

# 11. Low-confidence behavior

This is important.

Do not automatically mark weak matches as confirmed.

Recommended policy:

```text
high confidence
    → suggested

medium/ambiguous confidence
    → suggested + alternatives

low confidence / no useful candidate
    → no automatic match
```

Use:

```text
status = 'suggested'
```

for newly generated match candidates.

Do NOT create:

```text
status = 'confirmed'
```

automatically.

Do not automatically mutate `activity_progress`.

That belongs to Pass 10.

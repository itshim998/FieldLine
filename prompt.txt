# FIELDLINE — ENGLISH-ONLY CANONICAL PROJECT PROGRESS FIX

Repository:
itshim998/FieldLine

Target branch/commit:
main / 47295665adba286add44410cf9df926e9c818b96

We found a real product defect in the Live Voice reporting path.

Observed behavior:

Worker speaks in Bangla/Banglish:

"PR-B07 complete hoye geche"

Gemini Live correctly responds conversationally in Bengali, but FieldLine stores the project progress update as:

"PR-B07 complete hoye geche"

This is NOT acceptable.

REQUIRED PRODUCT INVARIANT:

The worker may speak in any supported natural language.

Gemini Live may continue responding conversationally in that language.

BUT every canonical FieldLine project progress update that enters the project-record / matching pipeline MUST be normalized to ENGLISH.

Examples:

Input:
"PR-B07 complete hoye geche"

Canonical stored project update:
"PR-B07 is complete."

Input:
"Pipe Rack PR-07 is 65% complete."

Canonical stored project update:
"Pipe Rack PR-07 is 65% complete."

Input:
"PR-B07 complete hoye geche, bolts ka kaam done"

Canonical stored project update:
"PR-B07 is complete; bolt installation work is finished."

Do NOT rewrite already-English text unnecessarily.

Current Live Voice system instructions explicitly say:

"When a worker reports completed or updated work, immediately invoke the 'record_field_progress' tool with their exact verbal statement."

The `record_field_progress(projectId, rawStatement)` tool currently receives the worker statement and sends it into the progress persistence / extraction / matching flow.

The current field-progress extraction prompt also receives the report as raw text and contains no English-normalization requirement.

Therefore the current implementation preserves the worker's original language into the project progress record.

=========================================================
3. CREATE A DEDICATED ENGLISH NORMALIZATION SERVICE
===================================================

Prefer a dedicated backend service, for example:

backend/src/ai/services/field-progress-normalization.service.ts

or an equally appropriate existing AI service location.

Do NOT put translation logic directly into the repository.

Do NOT put translation logic into the React frontend.

The normalization service should use the existing AIService abstraction rather than directly calling Gemini/Groq SDKs.

Existing AIService supports:

generateText(...)
extractStructured(...)

Prefer `extractStructured(...)` with a strict Zod schema.

Suggested schema:

{
"isEnglish": boolean,
"detectedLanguage": string,
"englishText": string
}

The normalization service should:

1. validate non-empty input
2. determine whether the source is already English
3. if English:

   * return the original text unchanged
4. if non-English or mixed-language:

   * produce a faithful English translation
5. preserve project-specific identifiers, activity codes, percentages, quantities, dates, locations, units, and technical terms
6. never invent missing facts
7. never convert "approximate" into exact values
8. never infer unstated progress
9. never perform activity matching
10. never change the semantic meaning of the report
11. return only the structured normalization result

=========================================================
4. NORMALIZATION PROMPT REQUIREMENTS
====================================

The prompt must explicitly say:

* The output `englishText` is the canonical internal project progress statement.
* The output MUST be in English.
* Preserve identifiers exactly.
* Preserve numeric values exactly.
* Preserve percentages exactly.
* Preserve dates exactly.
* Preserve quantities and units exactly.
* Preserve construction terminology.
* Do not summarize.
* Do not embellish.
* Do not infer.
* Do not invent.
* Do not change a worker's factual claim.
* Translate only enough to make the statement clear English.
* If the input is already English, return the text unchanged.

Examples must include:

"PR-B07 complete hoye geche"
→ "PR-B07 is complete."

"PR-B07 complete ho gaya"
→ "PR-B07 is complete."

"PR-B07 ka piling 65 percent complete hai"
→ "PR-B07 piling is 65 percent complete."

"Pipe Rack PR-07 is 65% complete."
→ unchanged.

=========================================================
12. FAILURE HANDLING
====================

If English normalization fails:

DO NOT silently persist the non-English statement as canonical project progress.

Preferred safe behavior:

* return a recoverable error state
* do not create a misleading canonical progress update
* inform the worker conversationally that the system could not safely normalize the report yet
* allow retry

Never silently fall back to storing Bangla/Banglish as canonical English progress.

If and only if the source is confidently already English, bypass translation and preserve it exactly.
